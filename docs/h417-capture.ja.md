# CH32H417 の GPIO 連続取り込み(実験の記録)

2026-10-21 の実験の記録。目標は、ポート 1 つ(16 ビット)を 20 MS/s で連続して取り込み、USB の SuperSpeed で流すこと。CH32RVLogicCapture の作りを決めるための材料にする。

計測の方法: 同じポートの PE3 に 100 kHz の PWM を出し、取り込んだデータの立ち上がりの間隔を全部調べた。PWM も取り込みのタイマーも 100 MHz から作るので、正しく取れていれば周期はいつも同じサンプル数になる。短い周期はサンプルが抜けた印。

## 結論

**TIM1 の 2 つの比較チャネルで DMA1 と DMA2 を半周期ずらして動かし、それぞれ 10 MS/s で取ると、合わせて 20 MS/s になる。** 2 本ともダブルバッファにし、DMA が書いている側と USB が読む側を別の SRAM のバンクに置けば、USB で 40 MB/s を流しながらでも抜けない。

- 30 秒 × 5 回(1506 万周期)で、ずれは 1 回(30 秒あたり約 0.3 回)だった。
- CPU はデータを写さない。CPU の仕事は割り込みと USB の転送を出すことだけ。
- ホストは、2 本の 32 KB の転送(A、B)を組にし、a0 b0 a1 b1 … と交互に並べ直す。

## 分かったこと

### SRAM は 128 KB のバンクに分かれている

共有 SRAM(0x20100000〜、512 KB)では、2 つの DMA が同じ 128 KB の範囲に当たったときだけ取り合いが起きた。ここで言う 2 つは、USB が読む側と、取り込みが書く側。

| 取り込み先 | USB が読むバッファ | 10 MS/s の抜け |
|---|---|---|
| 0x20140000 | 0x20120000(別のバンク) | 0〜1 ppm |
| 0x20140000 | 0x20150000 / 0x2015C000(同じバンク) | 1564〜1722 ppm |
| 循環バッファ 1 本を USB がそのまま読む | — | 1800〜2900 ppm |
| 循環バッファの 2 つの半分を、バンクの境目をまたいで置く(0x20138000) | 半分をそのまま | 0(9.09〜11.1 MS/s、300 万周期) |

### 1 本の DMA の限界

- タイマーの要求で周辺回路から読むと、1 回に HCLK(100 MHz)の 8 クロックかかる。1 本では 12.5 MS/s が上限。
- USB を流していなければ、12.5 MS/s でも抜けない。
- USB を流していると、バンクを分けても 12.5 MS/s では 1300〜2000 ppm 抜ける。同じバンクにいなくても効く取り合いがある。11.1 MS/s 以下なら 0。
- タイマーなしのメモリ間転送(CH32RVLogicCapture の captureBurst)は 1 回 5 クロック。ただし循環モードとダブルバッファモードが使えない。

### 2 本の DMA

- DMA1 と DMA2 は並んで動く。USB を流さずに、合わせて 25 MS/s(それぞれ 12.5 MS/s)まで正確だった。
- USB で流しながらでは、20 MS/s(それぞれ 10 MS/s)が抜けなかった。25 MS/s は 57% 抜けた。
- タイマーの比較値を 0 にすると、カウンタが動き出した最初の周期で要求が出るかどうかが、開始のたびに変わる。B が A より 1 サンプル先に進む回があった。比較値は 1 と 1 + P/2 にする。

### TCM

- DTCM(0x200C0000〜)と ITCM(0x200A0000〜)への DMA の書き込みは遅く、12.5 MS/s に追いつかない(ほぼ半分抜ける)。10 MS/s までは追いつく。
- USB が DTCM のバッファを読むと、取り合いの場所が DTCM に移り、かえって悪くなった。
- DMA1 のメモリ間転送では、DTCM から正しく読めなかった(データが崩れた)。
- DTCM・ITCM は V5F のメモリなので、ライブラリで使うならリンカーで確保する必要がある。今回の結論では使っていない。

### CPU で写す

- SRAM から SRAM へ 32 KB 写すと 410 µs(約 80 MB/s)、DTCM から SRAM へは 478 µs。
- 取り込み中のバンクを CPU が読みに行くと、それも取り合いになる(12.5 MS/s で 963 ppm)。

### ホストの受け取り

- 40 MB/s を Python で受け取りながら毎回解析すると、受け取りが追いつかない。デバイスは B を送れずに待ち、その間に DMA がそのバッファを書き換えてしまう(別の周回のデータが組になる)。
- デバイス側では、組の A を送った周回からバッファがもう一周していたら、B を送らずに組を捨てる。目印として、周回の番号を各バッファの先頭のサンプルに入れて確かめた(製品では、目印のために 1 サンプルを使わない形にする)。

## マルチコア(V5F)

今回は使っていない。今の H417 のボードは V3F だけを動かしている。

- 取り込みの速さ: V5F(400 MHz)が GPIO を読み続ける方式でも、GPIO の読み出しは同じバスを通るので、DMA より速くなる見込みは薄い。命令の流れで間隔が揺れるので、タイマーで刻む DMA より正確さも劣る。
- 使いどころ: 取り込んだデータのその場の処理。例えば、トリガーの検出、変化点だけを送る圧縮(ランレングス)、プロトコルの解読。DTCM を V5F のデータに使い、SRAM のバンクの取り合いに加わらない置き方にする。
- 試すには、V5F を起動する手順(EVT のデュアルコアの例)をコアに入れる必要がある。TODO の「V5F を使う形」と合わせて行う。

## ライブラリに入れるときの形(案)

- `startContinuous()` を 2 本の DMA で動かし、20 MS/s まで出す。バッファはライブラリがバンクを分けて置く。
- 1 本で足りる速さ(11.1 MS/s 以下)では、今の 1 本の形で、循環バッファの 2 つの半分をバンクの境目に置く。
- 受け取り側に、2 本を交互に並べ直す形で渡すか、デバイスで並べ直すか(CPU で 40 MB/s を並べ直す余裕があるかは未測定)を決める。
