# CH32H417 の 3 つのコア（V5F・V3F・PIOC）をどう組むか（調査）

2026-11-11 の調査の記録です。結論はまだ決めていません。最後に推奨と、決める前に測ることを書きます。

前提:

- 既定では、スケッチを V5F（400 MHz）で動かします（利用者の方針、2026-11-11）。V3F（100 MHz）は副として使える形にします。
- V5F で動かす試作は `CH32RV_RUN_V5F` で入っています（2a327705）。V3F は起動の数命令で V5F を起こして眠ります。

### 決める前に測ること

1. **全体の -march に B（Zba・Zbb・Zbs）を足すと、どれだけ速くなるか。** B は両方のコアにあるので、C2 と C3 の「共通の命令セット」に入れられます。
   - Xw（WCH-X）は、このコアの GCC（xpack 14.3 / 15.2）が知りません（`-march=..._xw` も `_xwchc` も「unsupported non-standard extension」）。WCH 版の GCC（MounRiver）を使わない限り、V5F だけの命令は実質ありません（2026-11-11 に試した）。
   - 関数単位なら `__attribute__((target("arch=+zbb")))` で拡張を足せます。`#pragma GCC target` は RISC-V では未対応で、警告が出て無視されます。XLEN と ABI は変えられません。
   - **属性の付いた関数は、属性の無い関数にインライン展開されました**（GCC 15 で、属性の無い関数に cpop が入った）。V3F から呼ぶ関数に紛れ込まないよう、拡張を足した関数には `noinline` も付けます。属性付きの関数を V3F から呼ぶと、実行中に不正命令で止まり、コンパイル時には分かりません。
2. **ITCM と DTCM に置くと速くなるか。** 今はコードもデータも共有 SRAM です（DMA が届くのは共有 SRAM）。割り込みと USB の処理だけを ITCM に置く形も測ります。
3. **V3F を待たせる方法。** IPC の割り込みと wfi で眠らせ、V5F から起動の要求を受けられるか。前の実験では「動いているコアを WAKEIP で起こし直す」ことができなかったので、起動の小片の中で待つ形を確かめます。
4. **V5F から V3F を止める方法と、止めたあとの再起動**（pico の `restartCore1()` に当たるもの）。
5. **BOOT 域のブートローダーから起動したとき（0x08000000 から）に、V5F の入口の番地が合うか。**
6. **デバッガ（ch32rv）で、V5F を選んで止める・進める手順。** docs/h417-multicore.ja.md の、選ばなかった hart が止まったまま残る件（0.22.1 で直った）も確かめ直します。

## 測った結果（2026-11-11、ベンチの H417）

### 1. -march に B（Zba・Zbb・Zbs）を足す

µs。libc はビルド済みのもの（B 無し）なので、memcpy、qsort、float は変わりません。

| 処理 | V3F | V3F + B | V5F | V5F + B |
|---|---|---|---|---|
| CRC（ビット演算） | 15,024 | 15,024 | 2,153 | 1,903 |
| popcount、ctz、andn | 122,210 | 26,058 | 18,035 | 4,016 |
| 配列の添え字の計算 | 8,232 | 8,229 | 1,721 | 1,377 |
| memcpy 640 KB | 10,693 | 10,694 | 4,526 | 4,528 |
| qsort 2000 個 | 5,761 | 5,763 | 2,277 | 2,278 |
| float | 387,559 | 387,558 | 64,917 | 64,287 |

B を足して遅くなったものは無く、コードは 552 バイト小さくなりました。両方のコアにあるので、全体の -march に入れられます。

### 2. コードを ITCM に置く

コード（.text）だけを ITCM に置き、データとスタックは共有 SRAM のままにしました（試験用のリンカースクリプト、crt0 が ITCM へ写す）。

| | 64 KB のコードを順に呼ぶ | 8 個の関数だけ（キャッシュに収まる） |
|---|---|---|
| V5F、コードは共有 SRAM | 24,530 µs | 9,461 µs |
| V5F、コードは ITCM | 9,860 µs | 9,453 µs |
| V3F | 29,218 µs | 28,484 µs |

- 命令キャッシュ（32 KB）に収まるうちは、置き場所で差はありません（上の測定の 6 種類も、ITCM と共有 SRAM で 1 µs も違わなかった）。
- 収まらないと、共有 SRAM では 2.5 倍遅くなり、V3F の 1.2 倍の速さしか出ません。USB やネットワークを使うスケッチは 32 KB を超えるので、V5F ではコードを ITCM に置くのがよさそうです。
- 決めること: ITCM（128 KB）を超えるときの扱い（DTCM もコードに使うと 384 KB まで、飛ぶたびに 1 待ち）、V3F で動かすコードの置き場所（V3F は ITCM を 2 HCLK で読む）、ビルドの最後に出る大きさの数え方（.itcm を数えていない）。

### 3. V5F から V3F を起動する

V3F の起動の小片（crt0）を次の形にしました。

1. 受け渡し用の語 `ch32rv_v3f_mailbox`（{関数, 引数, スタックの上端}、共有 SRAM の .bss）を 0 にする。
2. V5F を起こす。
3. PFIC_SCTLR の WFITOWFE を立てて wfi で待つ。
4. 目覚めたら語を見て、関数があれば V3F 用の CSR、gp、mtvec、mstatus（FPU 有り、割り込み無し）を整えて呼ぶ。関数が戻れば、また待つ。

V5F は、スタックと引数、関数の順に書き、PFIC_SCTLR の SETEVENT を立てます。

| 待ち方 | 結果 |
|---|---|
| WFITOWFE と SETEVENT | 動く。1000 回中 1000 回。要求から V3F の最初の書き込みまで 6.7〜9.3 µs（平均 7.8 µs） |
| ただの wfi | V3F は目覚めない（割り込みを止めているため） |
| 休みを入れて見回る | 動く |

途中で見つかったこと:

- **小片の番地の読み込みが、リンカーの relax で gp 相対に置き換えられた**（`addi t3, gp, 256`）。V3F は gp を設定していないので、別の番地を見回っていた。小片は `.option norelax` で囲む。
- **V5F で `csrr mcycle` を読むと例外になった**（V3F の `mhartid` も同じ）。時間は SysTick1 の数（0xE000F088、HCLK）で測る。

### 4. 止めて、もう一度起動する

関数が戻ると V3F は待ちに戻り、次の要求で同じように動きました（上の 1000 回は、毎回戻る関数）。V3F を外から止める仕組み（pico の `restartCore1()` に当たるもの）は、まだ作っていません。

### 共有 SRAM の取り合い

V5F には データキャッシュが無いので、休み無しで変数を読むと、そのバンクを使う V3F を押しのけます。V3F で 1 秒間、volatile の変数を数え上げた回数です。

| V3F のコードの場所 | V3F の変数 | V5F が delay() | V5F が wfi | V5F が休みを入れた見回り |
|---|---|---|---|---|
| 共有 SRAM | バンク 0（V5F の millis と同じ） | 12,700 | 1,000 万 | 999 万 |
| 共有 SRAM | バンク 3 | 416 万 | 1,110 万 | 771 万 |
| ITCM | バンク 0 | 555 万 | 833 万 | 556 万 |
| ITCM | バンク 3 | 832 万 | 908 万 | 528 万 |

- **今のコアの delay() は、millis の変数を休み無く読み続けるので、V3F がほぼ止まります。** V5F で動かすときは、delay() などの待ちに wfi か休みを入れます。
- 極端に止まるのは、V3F のコードと変数が、V5F の読む変数と同じバンクにあるときだけでした。V3F で動かすものは、V5F とは別のバンクにまとめるのがよさそうです。
- 共有 SRAM のバンクの調停を変える設定は、RM に見当たりませんでした（TCM には TCM_RRDUTY_CFGR などがある）。

### 5. BOOT 域のブートローダーから起動する

ブートローダーから起動すると、アプリは 0x08000000 側で動き、0x0 にはシステムのフラッシュが見えます。V5F の入口を 0x08000000 側（0x08000400）で渡しても、普通のリセットで V5F は起動しました。これなら、どちらの起動でも同じ番地で済みます。ブートローダーを入れた実際の起動は、まだ試していません。

### 6. デバッガ（ch32rv 0.30.1）

- `--core 1 dbg halt` / `regs` で、動いている V5F を止めて読めます。
- `dbg` の命令は、もう一方のコアを走らせ直しません（V5F をデバッグしたあと、V3F は止まったままで、起動の要求が通らなかった）。`dbg resume --all` で両方を戻すと、どちらを止めたあとも、起動の要求は 1000 回とも通りました。

| 物差し | P1 | P2 | P3 | P4 |
|---|---|---|---|---|
| 利用者の手間 | 無し（用意したプロトコルだけ） | 手元で組み立てて、ヘッダーを入れる | 無し | C++ で命令を並べる |
| OS をまたげるか | 問題無し | Python なら問題無し | WCH の道具は Windows 専用の 32 ビットの実行ファイル。自前のアセンブラなら可 | 問題無し |

- CH32X035 では PIOC のプログラムが本体の SRAM の 4 KB を使うので、ライブラリを使うときだけ、その 4 KB をスケッチの RAM から外す仕組みが要ります。H417 は別の場所なので要りません。
- コミュニティには、Rust の pioc（NKID00、アセンブラと逆アセンブラ、EVT の ASM と照合済み）、逆アセンブラの andelf/pioc、WASM53B を Wine で動かす devcontainer があります。ライセンスは確かめていません。

## 推奨（測る前の見込み）

**2 つのコア:** C1 を既定にし、その上に C3 を作り、C2 を C3 の上の書き方として用意します。

- V5F が主で、V3F は必要なときだけ起動します（利用者の方針どおり）。V3F を使わないスケッチは C1 と同じで、何も失いません。
- ビルドの仕組みを変えず、書き込みは 1 回です。型 2（Portenta）で多い「RPC が立ち上がらない」「片方だけ古い」という問題が起きません。
- 共通の命令セットにする前提です。今の GCC では Xw が使えないので、失うものは今のところありません。B は両方にあるので、全体の -march に入れられるかを 1 で測ります。
- Serial などのコアの機能は、まず V5F だけで使えるものとし、V3F からは IPC で V5F に頼む形を後から足します（ほかの例でも、2 つ目のコアに Serial を直接持たせたものは無い）。
- C4（コアごとに別ビルド）は、V3F で大きなプログラムを、別のコンパイルの設定で動かしたい用途が出たときの候補として残します。C3 の「番地を渡して起動する」仕組みの上に作れます。
- C6（SMP）は、命令セットと速さの違うコアに合わず、ライブラリをすべてスレッド安全にする費用に見合いません。

**PIOC:** P1 と P2 から始めます。

- ライブラリ（例えば CH32RVPioc）が、プログラムの読み込み、起動、停止、データの受け渡しを持ちます。
- 最初のプロトコル（ARGB の 1-Wire、UART など）は、自前で書いた ASM から作った配列を同梱します。
- アセンブラは Python で用意します。利用者は手元で組み立てて、生成したヘッダーをスケッチに入れます。
- H417 と CH32X035 で同じライブラリにし、X035 の RAM の 4 KB の扱いを入れます。
