# CH32H417 の 3 つのコア（V5F・V3F・PIOC）をどう組むか（調査）

2026-11-11 の調査の記録です。結論はまだ決めていません。最後に推奨と、決める前に測ることを書きます。

前提:

- 既定では、スケッチを V5F（400 MHz）で動かします（利用者の方針、2026-11-11）。V3F（100 MHz）は副として使える形にします。
- V5F で動かす試作は `CH32RV_RUN_V5F` で入っています（2a327705）。V3F は起動の数命令で V5F を起こして眠ります。

## H417 のハードウェアの条件（RM V1.8、EVT、実測）

| 項目 | 内容 | 出典 |
|---|---|---|
| リセットで動くコア | いつも V3F（C0）。起動するコアを選ぶ設定は見つからない | RM 4 章、EVT の Run_Core |
| 相手のコアを起こす | WAKEIP0（C0）と WAKEIP1（C1）に 1 KB 境界の番地を書き、PFIC_SCTLR の SETEVENT を立てる。動いているコアを起こし直すことは、前の実験ではできなかった | RM 4.7.5.51〜52、docs/h417-multicore.ja.md |
| 命令セット | 両方とも I、C、M、A、B、F。V5F だけ WCH-X（Xw）の拡張を持つ | RM 4 章の冒頭 |
| メモリ | ITCM 128 KB と DTCM 256 KB は V5F 用（V3F も 2 HCLK で読み書きでき、命令も読める）。共有 SRAM 512 KB は両方から待ち無し。ITCM と DTCM を合わせて V5F のコードに 384 KB まで使える | RM 1.2.1 |
| V5F の命令キャッシュ | 32 KB。リセットでは切れている（CSR 0xBC2 の bit 1）。共有 SRAM のコードも既定でキャッシュする | RM 4.2.3.9、試作で実測 |
| SysTick | コアごとに 1 つ（SysTick0 は 0xE000F000、SysTick1 は 0xE000F080）。状態の語は SysTick0 にあり共有 | EVT core_riscv.h、試作で実測 |
| コア間の通信 | IPC: 4 チャネル、チャネルごとに状態ビット 8 個と、受信と送信の割り込み（割り込み先のコアを選べる）、32 ビット × 4 のデータ。HSEM: 1 ステップと 2 ステップのロック | RM 4.4、4.5 |
| 割り込みの振り分け | PFIC_IALLOCR。割り込みを有効にしたコアへ振り直される | docs/h417-multicore.ja.md |
| PIOC | RISC8B の 8 ビットのコア。単一サイクルの 66 命令、システムクロックで動く。プログラム 2K ワード。2 本の I/O を扱う。H417 ではプログラム用の SRAM が 0x50040000 に別にあり、CH32X035 では本体の SRAM の 0x4000 から 4 KB を使う | RM 34 章、EVT の PIOC |

### 試作での実測（2026-11-11、ベンチの H417）

| 項目 | V3F | V5F（コードは共有 SRAM、命令キャッシュ有り） |
|---|---|---|
| CRC のループ（20000 回） | 13,621 µs | 2,103 µs（6.5 倍） |
| USB SS の bulk IN | 385 MB/s | 407 MB/s |
| UHSIF 200 MS/s × 16 本を PC へ | 約 1 割落ちる | 120 秒、平均 400.1 MB/s、周期の崩れ 11 か所 |

## 候補

### 2 つのコアの組み方

| 候補 | 形 | 近い例 |
|---|---|---|
| C1 | V5F だけで動かし、V3F は眠らせる（今の試作） | STM32duino の H7 |
| C2 | 1 つのスケッチ。弱いシンボル `setup1()` / `loop1()` があれば、V5F の準備のあとに V3F で動かす | arduino-pico |
| C3 | 1 つのスケッチ。V5F から実行中に関数とスタックを渡して V3F を起動する API。V3F は起動の小片の中で、IPC の割り込みを待って眠る | Pico SDK の `multicore_launch_core1()` |
| C4 | ボードの定義（またはメニューの「Target core」）を V3F 用と V5F 用に分け、別々にビルドしてフラッシュの別の場所に書く。V5F 側が V3F のイメージを起こす | Portenta H7 / GIGA |
| C5 | V3F 用のプログラムを別にビルドし、V5F のイメージに埋め込む | ESP-IDF の ULP、ESP-AMP |
| C6 | 1 つの RTOS で 2 つのコアを動かす（SMP） | ESP32 |
| C7 | V3F を主にしたまま、V5F を計算の助っ人として使う | 移行前の形、docs/h417-multicore.ja.md の実験 |

### PIOC のプログラムの作り方と読み込み方

| 候補 | 形 |
|---|---|
| P1 | 作った配列（EVT の `_inc.h` と同じ形）をライブラリに同梱し、実行中に memcpy で読み込んで走らせる |
| P2 | RISC8B のアセンブラを自前で用意する（Python、CHRISC8B.PDF に沿う）。利用者は手元で組み立て、生成したヘッダーをスケッチに入れる（arduino-pico の pioasm と同じ扱い） |
| P3 | ビルドの中でアセンブラを走らせる（フック） |
| P4 | 実行時に命令を組み立てる API（ESP32 の `ulp_macros.h` の形） |

### 決める前に測ること

1. **Xw（WCH-X）を使うと、V5F がどれだけ速くなるか。** C2 と C3 は、両方のコアに共通の命令セットでコンパイルする前提です。差が小さければ、共通の命令セットで失うものはありません。
2. **ITCM と DTCM に置くと速くなるか。** 今はコードもデータも共有 SRAM です（DMA が届くのは共有 SRAM）。割り込みと USB の処理だけを ITCM に置く形も測ります。
3. **V3F を待たせる方法。** IPC の割り込みと wfi で眠らせ、V5F から起動の要求を受けられるか。前の実験では「動いているコアを WAKEIP で起こし直す」ことができなかったので、起動の小片の中で待つ形を確かめます。
4. **V5F から V3F を止める方法と、止めたあとの再起動**（pico の `restartCore1()` に当たるもの）。
5. **BOOT 域のブートローダーから起動したとき（0x08000000 から）に、V5F の入口の番地が合うか。**
6. **デバッガ（ch32rv）で、V5F を選んで止める・進める手順。** docs/h417-multicore.ja.md の、選ばなかった hart が止まったまま残る件（0.22.1 で直った）も確かめ直します。

## 物差しでの比較（PIOC）

| 物差し | P1 | P2 | P3 | P4 |
|---|---|---|---|---|
| 利用者の手間 | 無し（用意したプロトコルだけ） | 手元で組み立てて、ヘッダーを入れる | 無し | C++ で命令を並べる |
| OS をまたげるか | 問題無し | Python なら問題無し | WCH の道具は Windows 専用の 32 ビットの実行ファイル。自前のアセンブラなら可 | 問題無し |
| ライセンス | 配列を作るのに使った道具とは無関係（自前で書いた ASM から作る場合） | 自前 | WCH の道具はライセンスの記載が無く、配れない | 自前 |
| 既存の資産 | EVT の ASM（UART、I2C、1-Wire、NEC、単線） | 同じ ASM が組み立てられる | 同じ | ASM は使えない |

- CH32X035 では PIOC のプログラムが本体の SRAM の 4 KB を使うので、ライブラリを使うときだけ、その 4 KB をスケッチの RAM から外す仕組みが要ります。H417 は別の場所なので要りません。
- コミュニティには、Rust の pioc（NKID00、アセンブラと逆アセンブラ、EVT の ASM と照合済み）、逆アセンブラの andelf/pioc、WASM53B を Wine で動かす devcontainer があります。ライセンスは確かめていません。

## 推奨（測る前の見込み）

**2 つのコア:** C1 を既定にし、その上に C3 を作り、C2 を C3 の上の書き方として用意します。

- V5F が主で、V3F は必要なときだけ起動します（利用者の方針どおり）。V3F を使わないスケッチは C1 と同じで、何も失いません。
- ビルドの仕組みを変えず、書き込みは 1 回です。型 2（Portenta）で多い「RPC が立ち上がらない」「片方だけ古い」という問題が起きません。
- 共通の命令セットにする前提なので、1 の測定で Xw の差が大きければ見直します。その場合でも、V3F で動く関数だけを別の命令セットでコンパイルする形（関数の属性）が残ります。
- Serial などのコアの機能は、まず V5F だけで使えるものとし、V3F からは IPC で V5F に頼む形を後から足します（ほかの例でも、2 つ目のコアに Serial を直接持たせたものは無い）。
- C4（コアごとに別ビルド）は、V3F で大きなプログラムを、別のコンパイルの設定で動かしたい用途が出たときの候補として残します。C3 の「番地を渡して起動する」仕組みの上に作れます。
- C6（SMP）は、命令セットと速さの違うコアに合わず、ライブラリをすべてスレッド安全にする費用に見合いません。

**PIOC:** P1 と P2 から始めます。

- ライブラリ（例えば CH32RVPioc）が、プログラムの読み込み、起動、停止、データの受け渡しを持ちます。
- 最初のプロトコル（ARGB の 1-Wire、UART など）は、自前で書いた ASM から作った配列を同梱します。
- アセンブラは Python で用意します。利用者は手元で組み立てて、生成したヘッダーをスケッチに入れます。
- H417 と CH32X035 で同じライブラリにし、X035 の RAM の 4 KB の扱いを入れます。
