# CH32H417 のデュアルコア(実験の記録)

2026-10-22 の実験の記録。V5F を使う形を設計するときに根拠にする数字を集めた。**設計はまだしていない。** コアには何も入れていない。

方法:
- V3F は Arduino のスケッチ(コアのまま、100 MHz)を動かす。
- V5F は、ITCM(0x200A0000)に置いた別のプログラムを動かす。起動のコードと命令の処理だけの小さなもので、スケッチとは別にビルドした。
- 2 つのコアは、共有 SRAM の 0x20170000 に置いた mailbox でやり取りする。V3F が命令と番号を書き、V5F が終わったら同じ番号を書き返す。
- 測定の指示は UART から V3F に送り、結果も UART で受け取った。

## 起動

| 項目 | 結果 |
|---|---|
| 起こし方 | `PFIC_WAKEIP1`(0xE000E724)に開始番地(1 KB 境界)を書き、`PFIC_SCTLR`(0xE000ED10)の bit 5(SETEVENT)を立てる。EVT の `NVIC_WakeUp_V5F` と同じ |
| CSTAR1(0xE000E784)の変化 | 起こす前 0xC000(深い眠り、ロック)→ WAKEIP1 を書くと 0x4000 → SETEVENT で 0(動いている) |
| 起こしてから V5F が最初の語を書くまで | 103 µs。うち 41,065 サイクル(103 µs)は V5F 自身の起動(.bss の 32 KB をゼロで埋める)。起こすことそのものは 1 µs 未満 |
| 起動直後のクロック | 起こして 16 ms 後から測って 399〜400 MHz(V5F の mcycle と V3F の micros() の比)。最初から 400 MHz |
| リセットのあと | `CH32RV.restart()` で V5F も深い眠りに戻り、また起こせた(3 回) |
| 動いている V5F をもう一度起こす | できない。ITCM を上書きして WAKEIP を書いても、V5F は動き直さなかった |

- V5F の起動のコードでは、割り込みを止めたまま(mstatus の MIE を 0)にし、mtvec を自分の例外処理に向ける。
  - EVT のとおり mstatus を 0x6088(MIE を 1)にし、mtvec を置かずに始めると、保留されていた割り込み(mcause 0x8000005D、TIM12)で V5F は 0 番地に飛んだ。
  - 0 番地にあるのは V3F のイメージで、V5F がその起動の処理を走らせて V3F を壊した。
- 32 番以上の割り込みの振り分け(`PFIC_IALLOCR`)は、リセット直後の値が決まっていない。読むと、多くが C1(V5F)向きだった。
  - 割り込みを有効にしたコアに、自動で振り直される(RM)。

### デバッガ(WCH-LinkE、ch32rv 0.22.0)との関係

- **ch32rv のコマンドは、選ばなかったほうのコアを止めたまま終わる。**
  - `--core 1 dbg resume` のあとは V3F がデバッグモード(CSTAR0 の bit 12)に残る。millis() は進まず、UART も応答しなかった。
  - コア 0 のコマンド(`read` も含む)は V5F を止める。V5F のループの回数で確かめた。止まるのは次のコマンドで接続した時点だった。
  - この間 V5F が「古い値を読む」と見えたのは、V5F が止まっていたためだった。
- 両方のコアを動かしたまま終えるには、1 回の接続の中で hart 1 を resume し(dpc を書いてから)、続けて hart 0 も resume する。
  - ch32rv のコマンドではできないので、ch32rv の crate を使う小さなツールを作業用に書いて確かめた。
- **LinkE が一度接続すると、コア 1 はデバッグモード(CSTAR1 の bit 12)のまま残る。**
  - リセットしても残り、WAKEIP では起きない。
  - DM を非活性にしてから(dmcontrol = 0)リセットすると、深い眠り(0xC000)に戻り、WAKEIP で起きた。
- LinkE の電源を入れ直したあとは、udev の board-identify がターゲットに接続する。そのせいで V3F が止まっていることがあった(docs/h417-bench.ja.md の 6.)。

## 速さ

| 項目 | V3F(100 MHz) | V5F(400 MHz) |
|---|---|---|
| 同じ C の計算(CRC と float の混ざったループ、200000 回) | 170〜184 ms | 32.0〜35.5 ms(12.8M〜14.2M サイクル) |
| 速さの比 | 1 | 4.9〜5.8 倍。クロックあたり 1.2〜1.4 倍 |
| volatile の変数を数えるループ | — | 1 回 12 サイクル |

ビルドごとのコードの置き場所で、V5F の時間は ±10% ほど変わった。V3F の時間は、V5F が mailbox を見回っていると少し遅くなる(下の「バスの取り合い」)。

## 共有メモリ

### mailbox の往復

- V3F が番号を書いてから、V5F の書き返しを V3F が読むまで 520〜630 ns(10000 回の平均)。
  - このときの V5F は、volatile のループ 16 回ぶんの休みを入れながら見回っている。
  - 別のビルドでは 1.33 µs だった。

### memcpy(V5F、32 KB、語単位)

| 元 → 先 | サイクル | MB/s |
|---|---|---|
| DTCM → DTCM | 41,004 | 319 |
| DTCM → SRAM | 41,003 | 319 |
| SRAM → DTCM | 49,219 | 266 |
| SRAM → SRAM(同じバンク) | 98,335 | 133 |
| SRAM → SRAM(別のバンク) | 81,955 | 159 |

V3F が SRAM から SRAM へ写すと約 80 MB/s(docs/h417-capture.ja.md)。

### バスの取り合い

V3F で同じ計算(50000 回)を走らせ、その間 V5F に一つの場所を読み続けさせた。V3F のコードとデータは SRAM のバンク 0(0x20100000〜)に、スタックはバンク 3(〜0x2017FFFF)にある。

| V5F がしていること | V3F の時間 |
|---|---|
| mailbox の見回り(バンク 3、休みあり) | 43.0 ms |
| DTCM だけで待つ | 43.1 ms |
| バンク 0(V3F のコード)を読み続ける(0.3 秒) | **300 ms** |
| バンク 2 を読み続ける | 43.1 ms |
| バンク 3(V3F のスタック)を読み続ける | 49.4 ms(15% 遅い) |
| DTCM を読み続ける | 43.1 ms |

- **V5F がバンク 0 を読み続けている間、V3F は止まった。** 300 ms は V5F が読み続けた時間そのもの。V5F のほうがバスで優先される。
- **休みを入れずに、V3F が書く語を V5F が待つと、チップ全体が止まった(3 回)。**
  - その語は mailbox と同じバンク 3 にあった。V5F が読み続けるので V3F がそのバンクに入れず、V5F の待つ語を書けなかった、とみている。
  - 止まるとデバッガも接続できない(`no target detected`)。LinkE の電源を入れ直し、リセットをかけたまま接続して戻した。
  - 100 サイクルに 1 回だけ読むように変えたら、同じ試験で止まらなかった。

## 原子操作と HSEM

### V5F だけ(100000 回)

| 命令 | DTCM | SRAM バンク 2 | ITCM | mailbox の語(バンク 3) |
|---|---|---|---|---|
| amoadd.w | 8.0 ns | 13.0 ns | 8.0 ns | 13.0 ns |
| lr.w / sc.w で加算 | 14.0 ns(sc の失敗 0) | 19.0 ns(sc の失敗 0) | — | — |
| amoswap.w | 10.0 ns | 15.0 ns | — | — |
| 普通の読み書きで加算 | — | 6.0 ns | — | — |

### 両方のコアで同じ語(バンク 3)を 1 ずつ増やす(それぞれ 200000 回)

| 方法 | 結果 | 1 回の時間 |
|---|---|---|
| amoadd.w | 400000 / 400000(失われない) | V3F 189 ns(1 つだけのときは 122 ns)、V5F 18.9 ns |
| 普通の読み書き | 300369 / 400000(25% が失われる) | V3F 85 ns、V5F 5.0 ns |

### HSEM(0xE000C000)

- ロックは「`HSEM_RLRx` を読んで 0 なら成功」(1 ステップ)、解除は「`HSEM_Rx` に 0 を書く」。
- ロックと解除の 1 組は、V5F だけで 50 ns、V3F だけで 70 ns。
- 両方のコアが、同じチャネルのロックの中で共有の数を普通の読み書きで増やす(それぞれ 100000 回)。
  - 200000 / 200000 で、排他は正しく働いた。
  - V3F は 28.1 ms(1 組あたり約 280 ns)。失敗した読み出しは V3F 174,370 回、V5F 75,192 回。

## GPIO

### 読み込み(GPIOE の INDR、16384 サンプル、PE3 に 100 kHz の PWM)

| ループ | 書き込み先 | 1 サンプル | 速さ | PE3 の周期(サンプル数) |
|---|---|---|---|---|
| 何も足さない(最初の版) | DTCM | 12.0 サイクル | 33.3 MS/s | 333〜334 |
| 何も足さない(最初の版) | SRAM | 14.0 サイクル | 28.6 MS/s | 285〜286 |
| nop を 0〜10 個 | DTCM | 16.0 サイクル | 25.0 MS/s | 250〜250 |
| nop を 12、16 個 | DTCM | 20.0 サイクル | 20.0 MS/s | 200〜200 |
| nop を 0〜10 個 | SRAM バンク 2 | 16.0 サイクル | 25.0 MS/s | 250〜250 |
| nop を 12、16 個 | SRAM バンク 2 | 28.0 サイクル | 14.3 MS/s | 142〜143 |

- 1 サンプルの時間は HCLK(100 MHz)の整数倍(V5F の 4 サイクル単位)にそろう。nop は、その段まではループの時間に入らない。
- 25 MS/s と 20 MS/s(DTCM)では、PE3 の周期が 16384 サンプルの間ずっと同じ数だった。抜けも揺れもない。
- mcycle で間隔を測って読む形は、1 サンプルに 20 サイクルより長くかかり、20 MS/s に追いつかなかった。間隔は命令の数で決める。
- 試したのは 16384 サンプル(0.65〜0.82 ms)だけ。V5F の割り込みは止めてある。

### 書き込み

- PE4 を `BSHR` で上げ下げすると、1 周期 8 サイクルで 50 MHz。

## 20 MS/s の取り込みとの関係(設計ではなく、分かったことの整理)

- docs/h417-capture.ja.md の 2 本の DMA の形は、20 MS/s を USB で流しながら、30 秒あたり約 0.3 回ずれる。
- V5F が GPIO を読む形では、20 MS/s と 25 MS/s が 1 サンプルの揺れもなく取れた(DTCM へ、短い時間)。
- 確かめていないことがある:
  - USB で流しながら同じことができるか。前の実験では、USB の DMA が DTCM を読むと取り合いが悪くなった。
  - DTCM(256 KB)に収まらない長さを、どこへどう渡すか。
- V5F が V3F のバンクを読み続けると V3F が止まるので、V5F の置き場所(コード、データ、待ちの仕方)は V3F のバンクを避ける必要がある。

## 測っていないこと

- V5F で取り込みながら USB(SS)で流す(SS のケーブルを抜いていた)。
- IPC(0xE000D000)による知らせと、その遅れ。V5F 側の割り込み(ベクター表を置き、MIE を 1 にした形)。
- 16384 サンプルより長い取り込みと、その間の V3F の動き(USB の割り込みなど)。
- V5F の命令キャッシュ。起動のコードで 0x20000000〜0x3FFFFFFF の分を切ったまま測った。ITCM のコードには関係しない。
- 消費電流。

## 試験に使ったもの(作業用、リポジトリには入れていない)

- V3F のスケッチ(Dual5): mailbox の命令と、上の表の測定。UsbFallback(DFU)付き。
- V5F のプログラム: `start.S`(スタック、mtvec、.bss、mcycle の記録)と `v5main.c`(命令の処理)。リンカーの設定で ITCM と DTCM に置く。
- 両方の hart を resume するツール: ch32rv の `ch32rv-wchlink` crate を使う。DM を非活性にする指定もある。
