# CH32H417 の UHSIF の解析

CH32H417 の UHSIF（Universal High-Speed Interface、最大 125 MHz・8〜32 ビットの並列バス）を、ロジアナの取り込みに
使えるかを調べた記録です。WCH はレジスタを公開せず、EVT の `libUHSIF.a`（ソースなし）だけを配っています
（[wch-evt-binary-libraries.ja.md](wch-evt-binary-libraries.ja.md)）。2026-11-11 の時点の結果で、**ライブラリを使わずに、
16 本のデータ線を内部クロックで、1 サンプルも抜けずに連続して取り込めました**（SYSCLK ÷ 2 = 200 MS/s、÷ 1 = 400 MS/s
を SRAM へ。最初のコミットの形ではバッファーごとに 8 サンプル抜けていて、直した。下の「DMA の続け方」）。これを [CH32RVUhsif](../libraries/CH32RVUhsif/README.ja.md) にまとめ、[CH32RVLogicCapture](../libraries/CH32RVLogicCapture/README.ja.md)
の `begin(UHSIF_DATA, rate)` がそれを使います（どちらも、WCH のライブラリのコードも FX3 SDK の文も含みません）。

調べ方:

- `libUHSIF.a` の逆アセンブル（コードは約 3 KB）。
- 実機（ベンチの H417 評価ボード、QEU6）で、ライブラリをリンクしたスケッチを動かし、レジスタを読み出しました。
  ライブラリが呼ぶ `GPIO_Init` は、端子に触らず引数を記録するだけの関数に差し替えています。出力の端子は駆動していません。

## 正体: Cypress FX3 の GPIF II と同じ作り

UHSIF のレジスタの並びと意味は、Cypress（Infineon）EZ-USB FX3 の GPIF II と PIB（socket と descriptor の DMA）に、
レジスタ単位で一致します。照らし合わせには、FX3 SDK のヘッダー（`gpif_regs.h`、`sock_regs.h`、`cyu3gpif.h`）を
参照用に読みました。FX3 SDK は Cypress のライセンスのもので、このリポジトリには写していません。

一致を確かめた点:

- 設定のレジスタは 76 個（0x000〜0x12C）で、FX3 の GPIF_CONFIG〜GPIF_BETA_DEASSERT と同じ範囲・同じ順です。
  ライブラリの表の値も FX3 の GPIF II Designer の出力と同じ形で、一部は値まで同じです（SERIAL_IN/OUT_CONFIG、
  THREAD_CONFIG、BETA_DEASSERT）。
- `UHSIF_Start()` は +0x118 と +0x11C のビット 0 を立てます。FX3 では WAVEFORM_CTRL_STAT.WAVEFORM_VALID と
  WAVEFORM_SWITCH です。
- 状態の記述子は、1 状態につき 12 バイトの左右 2 組で、フィールドの並び（次の状態、遷移関数への入力 FA〜FD、
  関数の番号 F0・F1、alpha、beta、繰り返しの回数、VALID）が FX3 と同じです。
- 入力（lambda）の割り当ても同じです。LAMBDA_STAT（+0x10C）の bit 28（常に 1）が実機で立っています。
- DMA は、RAM に置く 32 バイトの descriptor（バッファーのアドレス、sync、次の番号、大きさ）と、socket のレジスタ
  （SCK_DSCR、SCK_SIZE、SCK_COUNT、SCK_STATUS、SCK_INTR、SCK_INTR_MASK）です。descriptor の番号は
  「アドレス ÷ 32」です。

FX3 と違う点:

| 項目 | FX3 | UHSIF |
|---|---|---|
| ブロックの先頭 | 0xE0014000 | 0x40038000（RM の番地表にある 0x40013400 ではない） |
| 遷移関数（16 ビットの真理値表 × 32） | +0x130 | +0x180（+0x130〜0x17C は書いても 0 のまま。2026-11-14） |
| waveform のメモリ（左 / 右） | +0x1000 / +0x2000 | +0x2000 / +0x3000（0x4003A000 / 0x4003B000）、16 バイトおき |
| socket | PIB の socket | 0x40039000 + 0x100 × バッファー + 0x40 × 線。番号は 4 × バッファー + 線 |
| クロック | GCTL | RCC_CFGR2（+0x30）の UHSIFSRC（SYSCLK / PLL / USBHS の PLL / ETH の PLL）と UHSIFDIV |

## ライブラリの API がすること

| 関数 | すること |
|---|---|
| `UHSIF_GPIO_Init(mode, port_rm, clk_rm, div, width)` | RCC の UHSIF のクロックを有効にし、UHSIFDIV に div を書く。AFIO の PCFR1 に port_rm と clk_rm を書く。端子を `GPIO_Init` で設定する（master 16 ビットでは、データ 16 本が AF 出力、クロック PF11 と制御線が出力、いくつかが入力） |
| `UHSIF_Cfg()` | モード（master、slave の FPGA、slave の SOC）ごとの表で、76 個のレジスタ、遷移関数、waveform を書き込む（master は 11 状態、slave は最大 199 状態） |
| `UHSIF_Line_Cfg(line, dir, n, buf, wm)` | バッファー n 個（各 16 KB）の descriptor と socket を作り、THREAD_CONFIG に socket を結ぶ |
| `UHSIF_Start(on)` | WAVEFORM_VALID と SWITCH を立て、割り込みを有効にする。off は RCC で UHSIF をリセットする |
| `UHSIF_Trans_Cfg(line, idx, size)` | 終わったバッファーの socket を、もう一度動かす |
| `UHSIF_Reg_Cfg(mode, n, value)` | 0x40038000 + 4n に書いて読み返す（n は 0〜75） |
| 割り込み | バッファーが 1 つ終わるたびに、スレッドの socket を次（+4）に進め、`UHSIF_LineN_IN_Callback(バイト数)` を呼ぶ |

- ライブラリの割り込みの処理は、レジスタを自分で退避しない作りです（HPE が前提）。このコアの H417 は HPE を有効に
  しているので（INTSYSCR 0x07）、そのままベクターにつながります。
- ライブラリは soft-float の ABI、このコアの H417 は ilp32f です。ライブラリに浮動小数点のコードは無いので、
  ELF の ABI のフラグを書き換え、属性のセクションを外せばリンクできます。WCH 独自の命令（Xw）も含みます。

## 状態機械の意味（実機で確かめたこと）

FX3 の資料に書かれていない、または読み違えやすい点です。

- 状態の出力（alpha、beta）は、その状態に**入る遷移**で出ます。自分に戻る遷移では、alpha はもう一度は出ません。
- **alpha の bit 2 が、データ線の値をラッチします。** beta の bit 7（PUSH_WQ）は、ラッチした値を DMA に積むだけです。
  ラッチ無しで PUSH_WQ だけを出すと、前にラッチした値（リセットをまたいでも残る）が積まれ続けます。以前の「取り込んだ
  値が端子と合わない定数（0xFEF7 など）」は、これでした。
- 端子からの経路に、別の有効化（FX3 の IOMATRIX のようなもの）は要りません。データ線は、端子のモードに関係なく
  読めます（GPIO の入力でも、TIM3 の PWM を出している PC6 でも）。
- 1 サンプル / クロックにするには、2 つの状態を毎クロック行き来させ、両方への遷移で alpha の bit 2 と PUSH_WQ を
  出します。
- lambda の 0〜15 は制御線の端子の値、20 はデータのカウンターが上限、26 は DMA の準備（DMA_DREADY）、28 は常に 1
  です。遷移関数の表の番号は「a + 2b + 4c + 8d」（a〜d は FA〜FD の値）です。

### 左と右、1 段先の判断

- waveform のメモリは、状態ごとに左と右の 2 つの entry を持ちます。entry は 1 つの遷移で、入る先の状態（次の状態）と、
  そのときの出力を持ちます。
- **状態 s をどちらの entry で出るかは、s に入ってきた entry に書かれた入力（FA〜FD）と関数（F0、F1）で決まります。**
  s 自身の entry の FA〜FD と F0、F1 は、その entry の行き先の状態で使われます。FX3 と同じく、1 段先を読む作りです。
  実験: 状態 1 の左の entry の F1 だけを真にすると、右へ進むのは状態 1 ではなく、その次の状態でした。
- F1 が真で F0 が偽なら右、それ以外は左へ進みました（両方偽でも左へ進みました）。CH32RVUhsif は、F0 と F1 を
  互いに反対の表にしています。
- 通った entry の出力が出ます（通らなかった側の出力は出ません）。entry の alpha は w1 の 13:6 です（左右どちらの
  entry でも確かめました）。21:14 の意味は分かっていません。
- GPIF_CONFIG の bit 15（THREAD_IN_STATE）を立てると、PUSH_WQ の行き先のスレッドは、通った entry の beta の
  bit 5:4 で決まります。

waveform の 1 entry（16 バイト）のビットの並び:

| 語 | ビット | 中身 |
|---|---|---|
| w0 | 7:0 | 次の状態 |
| w0 | 12:8 / 17:13 / 22:18 / 27:23 | FA / FB / FC / FD（lambda の番号。次の状態の判断に使う） |
| w0, w1 | w0 31:28 と w1 0 | F0（左へ進む関数の番号、5 ビット） |
| w1 | 5:1 | F1（右へ進む関数の番号） |
| w1 | 13:6 / 21:14 | この entry の alpha / 不明 |
| w1, w2 | w1 31:22 と w2 21:0 | beta（32 ビット） |
| w2 | 29:22 / 30 / 31 | 繰り返しの回数（未確認） / beta を戻す / VALID |

### データのカウンター

- DATA_COUNT_CONFIG（+0x094）: bit 0 有効、bit 1 上限で戻す（reload）、bit 3 上へ数える、15:8 増やす量。
  RESET（+0x098）が戻す値、LIMIT（+0x09C）が上限です。beta の bit 16（INC_DATA）で +1、bit 17（RST_DATA）で戻します。
- reload を有効にすると、上限の印（lambda 20）は 1 クロックしか立たず、1 段先の判断に間に合いませんでした。reload を
  切り、上限で止まったカウンターを遷移の RST_DATA で戻します。
- RST_DATA は、その遷移で入った状態の判断にはまだ効きません（古い「上限」を見て、すぐに次も切り替えた）。リセットで
  入る状態は、カウンターを見ない状態にします。
- 1 つのバッファーを n サンプルにするには、上限を n − 2 にします（8189 と 8190 で 8192、8191 で 8194）。

### 割り込み

- beta の bit 18（INTR_CPU）で GPIF_INTR の bit 1 が立ち、INTR_MASK の bit 1 を立てておくと IRQ 145 が来ます。
- 各スレッドの socket の割り込み（GPIF_INTR の bit 11〜14）は、輪で回す使い方では使っていません。

## DMA の続け方

### 1 バッファーごとに止めて、割り込みで次へ進める（CH32RVUhsif の形）

- 1 つの socket に、descriptor を輪につなぎます（descriptor の 3 語目の下位 16 ビットが次の番号）。4 語目は
  「大きさ << 16 | 大きさ」で、byte count を最初から埋めておきます。
- SCK_SIZE（転送の大きさ）を 1 バッファーにし、SCK_STATUS は GO_ENABLE、SUSP_EOP、SUSP_TRANS、TRUNCATE
  （0x8C200000）、SCK_INTR_MASK は TRANS_DONE（bit 7）にします。socket はバッファーを 1 つ書くと止まり、
  GPIF_INTR の bit 11〜14（スレッドの socket の割り込み）を立てます。
- 割り込みでは、SCK_INTR の立っているビットを全部 1 で消し（SUSPEND と DSCR_IS_LOW を含む）、SCK_COUNT を 0 に
  して、SCK_STATUS の bit 30（GO_SUSPEND）を 1 回立てて戻します。socket は次の descriptor へ進みます。
- 止まっている間に来たサンプルは捨てられます。2 スレッドの交互の形なら、その間はもう片方が書いています。
- **socket を有効にしてから状態機械を動かすまで、少し待ちます。** すぐに動かすと、ビルドのたびに動いたり動かなかった
  りしました。100 µs 待つと、毎回動きました。

確かめ方: 取り込みの前にリング全体を目印（0xAAAA）で埋め、止めたあとに、目印の残りと、PWM の周期を調べました。
6.25、100、200 MS/s、塊 4096 と 32768 バイトで、目印は残らず、周期は境目と折り返しを含めてそろいました。

### 2 スレッドで交互に書く

スレッド 0 と 1 に別の socket と輪を持たせ、データのカウンターでバッファー 1 つごとにスレッドを切り替えます。片方の
socket が止まって再開を待つ間、もう片方が書いています。状態は 4 つです（a = lambda 20）。

| 状態 | 判断 | 左 | 右 |
|---|---|---|---|
| A0 | いつも左 | → B0（スレッド 0、+1） | — |
| B0 | a なら右 | → A0（スレッド 0、+1） | → A1（スレッド 1、リセット、割り込み） |
| A1 | いつも左 | → B1（スレッド 1、+1） | — |
| B1 | a なら右 | → A1（スレッド 1、+1） | → A0（スレッド 0、リセット、割り込み） |

どの遷移もラッチして積みます。CH32RVLogicCapture の `begin(UHSIF_DATA, rate)` が、この形です。1 スレッドだけだと、
socket が止まっている間（割り込みで再開するまで）のサンプルが抜けます。

### 止めずに回し続ける形では、どのバッファーも最後の 16 バイトが抜ける

最初に使った形です（2026-11-11 の最初のコミット）。SCK_SIZE を 0（大きさ無し）、SUSP_* を立てず、byte count を
埋めた descriptor の輪にすると、socket は CPU 抜きで回り続けます。ただし:

- どのバッファーも、最後の 16 バイト（8 サンプル）が書かれませんでした（目印が残る）。
- 周期 1000 サンプルの PWM で境目の位相を測ると、ちょうど 8 サンプル飛んでいました。書かれなかった位置のサンプルは、
  捨てられています（後ろへずれてもいない）。
- 状態機械のカウンターの上限を変えても、descriptor の大きさの欄を 16 増やしても、直りませんでした。byte count の欄を
  増やすと CPU が止まりました。
- 周期 16 や 512 の PWM では、抜けた 8 サンプルが PWM の low の間に重なると、周期の確かめでは見えません。最初の
  確かめはこれで通ってしまいました。

### byte count を 0 にした場合

FX3 の本来の形（埋まったバッファーは使用中になり、CPU が空ける）に見えます。各 socket は最初の 1 周だけ書いて止まり、
descriptor を書き戻しても、SCK_EVENT（socket の +0x3C）に番号を書いても、動き出しませんでした（書き方によっては
CPU が止まった）。

### 大きさと位置

- バッファーの大きさが 32 の倍数でないと（4112、32784 バイト）、始めた直後に CPU が止まりました。DMA がバッファーの
  外に書いたとみています。CH32RVUhsif は 64（スレッドの burst）の倍数を求めます。
- 65520 バイト（64 の倍数でない）では、毎回、塊の先頭の近くでデータが崩れました。

### データのカウンターの上限

例の状態機械（A がカウンターを見ず、B が見る）では、スレッドは「上限 + 2」サンプルを積んでから切り替わります。
1 バッファー n サンプルなら、上限は n − 2 です。

## 速さ（2026-11-11、ベンチの H417、SYSCLK 400 MHz）

### SRAM へ

| クロック | 結果 |
|---|---|
| 6.25、100、200 MHz | 抜け無し（上の確かめ方） |
| 400 MHz（SYSCLK ÷ 1） | 800 MB/s で流れた。390 kHz の PWM の 1 周期が 1 か所だけ 2 つに割れた（端の近くを取ったときの乱れとみている）。RM の UHSIF の仕様は 125 MHz まで |

### USB SuperSpeed で PC へ

測り方: デバイスは 8 個 × 32 KB のリングを 2 スレッドで埋め、埋まった連続の区間をまとめて `writeDirect()` で送り
ます（送り終わる前に輪が一周しそうなら、古い分を捨てる）。PC は libusb の非同期の受信（4 MB × 8 個）で受け取り、
DATA9 に出した 300 kHz の PWM の周期を全部調べます（周期が塊の長さを割り切らないので、塊が丸ごと落ちても分かる）。
USB の処理は V3F（100 MHz）で、ハブを 1 段はさみます。

| 取り込み | 必要な量 | 受け取れた量 | 30 秒の落ち |
|---|---|---|---|
| 100 MS/s（SYSCLK ÷ 4） | 200 MB/s | 203 MB/s | 0（始まりの部分の 3 か所を除く） |
| 133 MS/s（SYSCLK ÷ 3） | 267 MB/s | 268 MB/s | 0（始まりの 1 か所を除く） |
| 160 MS/s（USBHS の PLL ÷ 3） | 320 MB/s | 320 MB/s | 8 秒で数か所 |
| 200 MS/s（SYSCLK ÷ 2） | 400 MB/s | 約 365 MB/s | 約 1 割 |

- 取り込み無しで USB だけを流すと、1 秒に 375〜392 MB/s でした。bMaxBurst を 4 から 16 にしても同じでした。
- UHSIF が別のバンクに 400 MB/s で書いていても、USB は 366 MB/s 出ました。バスの取り合いではなく、USB の chain
  （16 パケット = 16 KB）ごとに割り込みで次を仕掛ける間の待ちが効いているとみています。
- 前半と後半の 2 つだけ（CH32RVLogicCapture の今の API）では、1 回送るたびに「完了 → 次」の待ちが入り、100 MS/s で
  も送り終わる前に上書きされる半分が出ました。PC へ流すには、もっと深いリングが要ります。
- 測定の途中で UART に表示させると（115200 bps で数ミリ秒、ループが止まる）、リングの余裕（約 1 ms）を超えて落ちます。

## FX3 由来の機能の確認（2026-11-14）

FX3 の GPIF II には、取り込みのほかに、比較器、カウンター、直列の入出力、CRC、DDR、端子の割り当ての設定があります。UHSIF で
どこまで使えるか、特に「任意の端子を任意のビット位置で取る」「USB に出す量を詰め替えて減らす」に使えるものがあるかを、
ベンチの H417（6-2、oep e8f60ae84dc2、`vio18=3v3`）で確かめました。

### 測り方

- 実験用のスケッチ（DMSeq のコンソール）で、レジスターの読み書き、状態機械、リング、端子の駆動をコマンドで操り、
  ホストの Python から実験を組みました。スケッチと手順は、このリポジトリには入れていません（使い捨て）。
- 端子と口（UHSIF_PORT0〜47、RM の表 9-33 の PORT_RM = 00）の対応は、DUT 自身が 48 本の端子を 1 本ずつ High にし
  （walking 1）、設定ごとに取り込んだ値のどのビットが立つかで調べました。
- 速さと比較器は、DUT のタイマーの PWM（PD12〜PD15 で出る）と `tone()` で調べました。プローブの PWM（PA13 / PA14）でも
  同じ結果でした。
- 1 回だけの取り込みは、データのカウンターが上限に来たら積まない状態に移る形にしました。バッファーが 1 つの輪を回し続けると、
  止めたときに新しい分と古い分の継ぎはぎになり、「サンプルの抜け」「偽のパルス」に見えたためです（下の「気を付けること」）。

### レジスターの有無

設定のレジスターに全ビット 1 を書いて読み返しました（書けるビット）。

| レジスター | 書けるビット | 実験の結果 |
|---|---|---|
| CONFIG（+0x000） | — | 比較器の有効（bit 0 / 2）、ENDIAN（bit 10）、比較器の変化のモード（bit 13）が効く。DDR（bit 6）、SERIAL_MODE（bit 14）は効かない |
| BUS_CONFIG（+0x004） | ffffffff | 幅（3:2）、bit 21 でデータのビットの並びが逆（WCH の追加）、bit 23（CE_CLKSTOP）で CTRL0 がクロックを止める。PIN_COUNT（1:0）、ADR_CTRL（8:5）など、ほかは取り込みに影響なし |
| BUS_CONFIG2（+0x008） | 1f1f1f07 | 調べていない（制御線を状態の番号にする機能） |
| AD_CONFIG（+0x00C） | 000f03ff | AIN_SELECT = 1 でアドレス入力（制御線の端子）が INGRESS_ADDRESS に入る。DMA へは積めなかった |
| SERIAL_IN / SERIAL_OUT（+0x01C / 0x020） | 0 | **無い**。SERIAL_MODE を立てても 16 ビットの並列のまま |
| CTRL_BUS_DIRECTION / DEFAULT / POLARITY / TOGGLE / SELECT（+0x024〜0x070） | ある | 制御線の出力の設定。FX3 と同じく CTRL_BUS_SELECT は出力に何を出すかの選択で、入力の端子は選べない。出力は試していない |
| 制御・アドレス・状態・データのカウンター（+0x074〜0x09C） | ある | データのカウンターは使っている。ほかは試していない |
| 制御・データ・アドレスの比較器（+0x0A0〜0x0B4） | ある | 制御とデータは動く（下） |
| WAVEFORM_SWITCH_TIMEOUT（+0x120） | ffffffff | 試していない |
| CRC_CONFIG / CRC_DATA（+0x124 / 0x128） | 0 | **無い** |
| +0x130〜0x17C | 0 | 書けない |

### 端子とビット: 割り当ては決まっている

| 設定 | データのビット ← 口 | 1 サンプル |
|---|---|---|
| 幅 8（BUS_CONFIG 3:2 = 0） | ビット 0〜7 ← PORT16〜23 | 1 バイト（1 語に 4 サンプル、DATA0 が下位） |
| 幅 16（= 1、今までの形） | ビット 0〜15 ← PORT16〜31 | 2 バイト |
| 幅 24（= 2） | ビット 0〜23 ← PORT16〜39 | 3 バイトずつ語をまたいで詰める（最初の語はずれて見えた。調べ切っていない） |
| 幅 32（= 3） | ビット 0〜31 ← PORT16〜47 | 4 バイト |
| BUS_CONFIG bit 21 | 並びが逆（16 ビットでビット 0 ← PORT31 … ビット 15 ← PORT16） | — |
| CONFIG bit 10（ENDIAN） | 16 ビットの中で上下のバイトが入れ替わる | — |

- データはいつも PORT16 から始まります。WCH の開発資料（EVT の `UHSIF Development Reference Manual`）は「DATA[31:0] は
  PORT[31:0] か PORT[47:16]」と書いていますが、PORT0 から始める設定は、BUS_CONFIG・BUS_CONFIG2・AD_CONFIG・CONFIG の
  全ビットを 1 本ずつ立てても見つかりませんでした。
- 制御線の入力は **CTRL n ← PORT(15 − n)** で決まっています（CTRL0 = PB14 … CTRL15 = PF12）。ADR_CTRL を変えても
  変わりません。WCH の資料の「アドレス線と制御線は柔軟に割り当てられる」は、状態機械でどの制御線を何に使うかのことで、
  端子の選択ではないと見ています。
- AFIO の UHSIF_PORT_RM（RM の表 9-33）は PORT0〜7 の端子を付け替えるだけで、データ線（PORT16〜）は変わりません。
- **結論: 任意の端子を任意のビット位置で取る経路は、ハードウェアにありません。** 取れるのは、幅で切った PORT16 からの
  ひと続きと、その逆順・バイトの入れ替えだけです。「任意の 8 本を任意の順番」にするには、端子を PD10〜PD15、PF0、PF1
  に配線するか、取り込んだあとに CPU で並べ替えます（V5F の SRAM 間のコピーは 133〜159 MB/s で、200 MS/s × 2 バイトには
  届きません）。

### 幅ごとの速さ

PD12 の PWM（約 390 kHz、半周期の期待値は 100 / 200 / 400 MS/s で 128 / 256 / 512 サンプル）を、1 バッファーずつ取り込みました。

| 取り込み | 8 ビット | 16 ビット | 32 ビット |
|---|---|---|---|
| 100 MS/s（SYSCLK ÷ 4） | 128、抜け無し | 128、抜け無し | 128、抜け無し |
| 200 MS/s（÷ 2） | 256、抜け無し | 256、抜け無し | 256、抜け無し |
| 400 MS/s（÷ 1） | 512、抜け無し | 512、抜け無し | 512、抜け無し |

- 32 ビット・400 MS/s は 1.6 GB/s の書き込みです。1 バッファー（4 KB）では通りましたが、続けて流せるかは確かめていません。
- クロックの正確さ: SYSCLK が HSI の PLL のとき、プローブの 10 kHz の PWM は 6.25 MS/s で半周期 315 サンプル（期待 312.5、
  +0.8%）でした。Clock Source を水晶（HSE、25 MHz。H41x の既定にした）にすると 312 / 313 サンプルで、ずれが消えました。
- 8 ビット・200 MS/s は 200 MB/s で、USB SS の bulk IN（約 400 MB/s）に余裕を持って入ります。16 本が要らないときの
  「USB に出す量を減らす」は、これがいちばん素直です。

### 比較器: 動く

| 機能 | 結果 |
|---|---|
| データの比較器（一致） | lambda 23 が「マスクのビットが値と同じ」で真。状態機械が止まっていても端子の今の値に従う |
| データの比較器（変化。CONFIG bit 13） | 動く。**マスクの意味が FX3 の資料と逆**で、1 のビットが無視され、0 のビットが見張られる。浮いた端子のノイズも変化として拾う |
| 制御線の比較器（一致） | lambda 21 が「マスクの制御線が値と同じ」で真（CTRL0 = PB14 で確かめた） |
| エッジのトリガー | 「一致しない」を待ち、「一致する」を待ってから取り込むと、最初のエッジが半周期後（312 / 313 サンプル、10 kHz・6.25 MS/s）に来た。立ち上がりの瞬間から取れている |
| 変化したときだけ積む | 積まれた値は 1 つずつ交互に変わり、重複が無い。ただ変化した時刻は残らない |

- 比較器で待つ段も、2 つの状態を行き来させます。同じ状態へ戻る遷移では判断し直さないためか、1 つの状態で待つと先へ進み
  ませんでした。
- 変化したときだけ積む形に時刻を付ける方法は、見つかりませんでした。カウンターの値を DMA に積む経路が無いためです
  （DOUT_SELECT はカウンターを出力の側につなぐもの）。時刻の無い変化の列は、遅いバスの状態の並びを見るぐらいにしか
  使えないので、ライブラリには関数（`setDataChange()`）だけを入れ、例は作っていません。

### 効かなかったもの

| 機能 | 結果 |
|---|---|
| 状態の繰り返し回数（entry の w2 29:22） | 書けて読み返せるが、取り込みの間隔は変わらない |
| DDR（CONFIG bit 6） | 変わらない |
| 直列入力（SERIAL_MODE と SERIAL_IN_CONFIG） | レジスターが無い |
| CRC | レジスターが無い |
| アドレス入力を DMA へ積む（PUSH_AWQ、AIN_SELECT = 2） | 積まれない。INGRESS_ADDRESS（CPU が読むレジスター）には入る |

間引き（遅い取り込み）は、クロックの分周（÷ 1〜64、源は SYSCLK か USBHS の PLL）と、積まない状態をはさむ鎖（255 状態まで）で作れます。

### ライブラリに入れたもの

実用になるものだけを CH32RVUhsif に入れました。

- `setBusWidth(8 / 16 / 32)`。24 ビットは詰め方が半端なので入れていません。
- `setDataMatch(value, mask)`、`setDataChange(watch)`（マスクの反転は中で吸収）、`setControlMatch(value, mask)`、
  状態機械の入力 `DataMatch`（23）と `ControlMatch`（21）。
- 例 UhsifTrigger: DATA2 の立ち上がりでトリガーし、8 ビット幅・200 MS/s で 4096 サンプルを 1 回取る（6-2 で、100 kHz・
  duty 1/4 の PWM が High 500 / 周期 2000 サンプル、未書き込み 0）。

入れていないもの: ビットの逆順とバイトの入れ替え（使い道が狭い）、制御線とアドレスの入力を CPU が読むこと（遅い）。

### 気を付けること（この調査で分かったこと）

- **積むのをやめると、最後の 64 バイトに満たない端数がブロックに残り、書き出されません**（スレッドの burst が 64 バイト）。
  1 回だけの取り込みでは、欲しい分より 64 バイト多く積みます。16 ビットでも 8 ビットでも、最後の 32 バイトが残りました。
- バッファーが 1 つの輪で取り続けると、ライブラリの割り込みが同じバッファーへ書き直させ続けるので、止めた時点の中身は
  継ぎはぎになります。最初はこれを取りこぼしと読み違えました。
- 実験の途中で、全部の口を GPIO の出力にしたまま入力に戻し忘れると、プローブの PWM と出力がぶつかります（PA13 の信号が
  消えた）。

## ベンチで気を付けること

- **UHSIF が動いたままだと、LinkE での書き込みが `transfer-failed`（読み返しが合わない）で失敗します。** CPU を止めても
  DMA は止まらず、RAM に置いた書き込み用のローダーを上書きするためとみています。書き込む前に、スケッチ側で UHSIF を
  止めます（試験のスケッチは UART の `stop`）。

   近づける。
2. CH32RVLogicCapture に、PC へ流すための深いリング（4〜16 個の塊）を入れる。
3. 速い信号での確かさ（外の発振器か OEP のプローブで 50〜200 MHz）。
4. w1 の 21:14、外部クロック、出力の向き、byte count を 0 にした本来の受け渡し。幅（8 / 32）、比較器のトリガー、繰り返しの
   回数（効かない）は上の「FX3 由来の機能の確認」。32 ビット・400 MS/s を続けて流せるか。
