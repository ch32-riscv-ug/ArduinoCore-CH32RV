# R-23: TinyUSBのベンダヘッダ依存をどう外すか(議題・レビュー用)

日付: 2026-08-21
状態: **決定(2026-08-21、ユーザ指示)。まずB、A'はずっと先**
関連: [ADR-0012](../adr/0012-usb-stack.ja.md)、[R-22](usb-stack.ja.md)、[ADR-0003](../adr/0003-owned-startup-vector-linker.ja.md)

## 議題

TinyUSBのCH32ドライバは、一部のfamilyについて**WCHのSDKヘッダをincludeする**。
このコアは[ADR-0003](../adr/0003-owned-startup-vector-linker.ja.md)でEVTを同梱しない方針なので、
このままでは噛み合わない。**どう外すか**を決めたい。

急がずに扱う理由は、選択肢の1つが**上流への変更提案**であり、
既存ユーザーへの影響と、上流が納得するかどうかを見誤ると差し戻しになるため。

## 事実: 依存しているのは4つだけ

`src/portable/wch/`のドライバ3本(`dcd_ch32_usbfs.c` 592行、`hcd_ch32_usbfs.c` 661行、
`dcd_ch32_usbhs.c` 465行)がベンダ側に求めているものを数えた。

| # | 記号 | 用途 | 出どころ | このコアに相当物は? |
|---|---|---|---|---|
| 1 | `USBOTG_FS` / `USBFSD` / `USBHSD`(structとポインタ) | レジスタアクセス | `ch32_usbfs_reg.h`が`#include <ch32v20x.h>`等で得る | **無い**(作るなら書く) |
| 2 | `USBFS_IRQn` / `USBHS_IRQn` / `USBHD_IRQn` | 割込み番号 | ベンダヘッダの`IRQn_Type` | **ある**。生成した`CH32_IRQN_USBFS`等 |
| 3 | `NVIC_EnableIRQ` / `NVIC_DisableIRQ` | 割込み許可 | WCHの`core_riscv.h` | **ある**。`ch32_irq_enable/disable` |
| 4 | `SystemCoreClock` | 2箇所 | ベンダの`system_*.c` | **ある**。`F_CPU` |

つまり**本当に無いのはレジスタstructだけ**で、残り3つは名前を合わせるだけ。
逆に言えば、**structだけ上流で自前化されても、2〜4のために結局こちら側で
小さなヘッダを用意することになる**。ここは見落としやすい。

なお、structを既に自前で持っているportもある(**CH32V103とCH58x**)。
`ch32_usbfs_reg.h`には上流自身のTODOがある。

```text
// TODO unify into a single struct shared by all WCH USBFS parts.
```

### ただし最新の貢献は逆を向いている

未マージのPR #3703(CH32X035)は、自前structではなく**ベンダヘッダを読む側**に倣っている。

```c
#elif CFG_TUSB_MCU == OPT_MCU_CH32X035
  #include <ch32x035.h>
  #define USBOTG_FS USBFSD
  #define USBHD_IRQn USBFS_IRQn
#endif
```

TODOがあることと、**実際の流れがそちらへ向かっていることは別**。
提案するならこの差を踏まえる必要がある。

## 選択肢

### A. 上流でstructを自前化する(全WCH portの統一)

- ○ 上流自身のTODOと一致する。V103とCH58xという前例もある
- ○ 恒久的に解決する。**forkを持たない**という[ADR-0012](../adr/0012-usb-stack.ja.md)の方針にも沿う
- ○ TinyUSB側の利点として「BSPを持たない統合でもportが使える」と言える
- ✗ **V20x/V30x/F20x/X035に横断で手を入れる**refactorになる。レビュー負荷が大きい
- ✗ **既存ユーザーへの影響**: 今のBSPはどのみちベンダヘッダを読むので直接は壊れない見込みだが、
  driverからの推移的includeに依存しているコードがあれば壊れる。**要調査**
- ✗ structの写し違いは**動く/動かないではなく、たまに壊れる**形で出る。
  検証をどう示すかが要る(全familyの実機は上流にも無い)
- ✗ **2〜4は解決しない**。IRQn・NVIC・SystemCoreClockは結局ベンダ側の名前のまま
- ? 上流が納得するか: **TODOは書いてあるが、直近のPRは逆方向**。
  「なぜ今それが必要か」を説明できないと通らない。
  こちらの動機(EVTを同梱しないコア)は上流にとっては他人事なので、
  **上流にとっての利点**(vendor SDKなしでビルドできる、BSP以外の統合が楽になる)で語る必要がある

### A'. 上流に「ベンダヘッダを使わない」道を1本足す(既定は現状のまま)

Aの全面refactorではなく、**opt-inのスイッチ**を足す形。

```c
#elif CFG_TUSB_MCU == OPT_MCU_CH32V20X
  #if defined(CFG_TUSB_WCH_SELF_CONTAINED_REG)
    /* 自前struct(V103やCH58xと同じ書き方) */
  #else
    #include <ch32v20x.h>      /* 既定。既存ユーザーは何も変わらない */
  #endif
```

- ○ **既存ユーザーへの影響がゼロ**。既定を変えないので、レビューで問われる点が減る
- ○ PRが小さい。1 familyずつ足せる
- ○ 「vendor SDKを持たない統合でも使える」という上流にとっての利点は同じ
- ✗ `#if`が増える。上流が「TODOは統一と書いたのに分岐を増やすのか」と見る可能性
- ✗ 2〜4(IRQn/NVIC/SystemCoreClock)は依然として残るので、
  **こちら側の小さなヘッダは結局要る**

### B. 同名のヘッダをこちら側で用意する(shim)

`#include <ch32v20x.h>`が解決できればよいので、**その名前のヘッダを自分で置く**。
中身は上の1〜4だけ。

- ○ **上流と交渉せずに今日できる**。TinyUSBは無改造のまま使える
- ○ 中身は小さい。structだけ書けばよく、2〜4は既存の生成物から名前を貼るだけ
- ○ 2〜4も同じヘッダで一緒に片付く(名前を合わせるだけ)
- ✗ **偽のベンダヘッダ**であることが読み手に伝わりにくい。名前で誤解される
- ✗ TinyUSBが**新しいベンダ記号を使い始めた瞬間に壊れる**。追随の義務が生じる
- ✗ ユーザーが本物のEVTヘッダを同じpathに置いた場合、**どちらが勝つかがinclude順次第**
- ✗ family(=variant)ごとに1つずつ要る。将来9 seriesに増える

**置き場所は`variants/<SERIES>/`が素直**だと分かった。arduino-cliはvariantディレクトリを
include pathへ入れる(`pins_arduino.h`がそこから解決されている)ので、
`variants/CH32V203/ch32v20x.h`を置けばTinyUSBの`#include <ch32v20x.h>`は解決する。
family差もvariant単位で自然に表現でき、**生成物として出せる**。
副作用は「sketchからも`#include <ch32v20x.h>`が見えてしまう」ことだが、
これは`pins_arduino.h`と同じ性質で、実害は小さい。

なお**libraryの`src/`配下のサブディレクトリはinclude pathに入らない**ので、
`libraries/USB/src/wch-shim/`のような隔離はできない。隔離したいならvariant側になる。

### C. EVTヘッダを同梱する

- ✗ [ADR-0003](../adr/0003-owned-startup-vector-linker.ja.md)に反する。
  1ヘッダで済まず、`core_riscv.h`など一式が付いてくる

### D. Bで動かし、実績を持ってAを提案する

- ○ **止まらない**。Aの提案時に「実際にこう困った、こう回避した」という材料が付く
- ○ Aが通ればBを捨てられる。通らなくても動いている
- ✗ 一時的に2つの経路を抱える
- ✗ 「一時的」が長引きやすい

## まだ調べていないこと(判断の前に潰したい)

      頼っていないので、structを自前化してもin-treeのBSPは壊れない。
      壊れうるのは「driver経由でベンダヘッダが来ることを当てにしていた
      out-of-treeの統合」だけで、それも**コンパイルエラーとして出る**(黙って壊れない)
- [ ] Aを提案するなら**どこまでを1つのPRにするか**。
      「V20xだけ」か「WCH全部」か。小さいほど通りやすいが、統一の主張は弱くなる
- [ ] 上流の温度感。TODOを書いた本人(HiFiPhile/hathach)に**issueで先に問う**のが安全か、
      いきなりPRを出すか
- [x] **Bのshimをどこへ置くか**(調査済み): `variants/<SERIES>/`。arduino-cliが

      **libraryの`src/`配下サブディレクトリはinclude pathに入らない**ので隔離はできず、
      sketchからも見える点は`pins_arduino.h`と同じ性質として受け入れることになる
- [ ] shimのstructを**どう検証するか**。EVTヘッダとoffsetを突き合わせる自動チェックは

## 現時点の所感(決定ではない)

**B(variantに置くshim)で動かし、必要になったらA'を提案する**、が今のところ妥当に見える。
根拠を整理すると:

1. 依存の実体は**structだけ**。残る3つはこちらに相当物があり、名前を合わせるだけ。
   つまり**どの案を採ってもshim相当のヘッダは要る**。
   ならば「まずshim」は追加コストがほぼ無い
2. 置き場所が`variants/<SERIES>/`で解決する。**生成物にできる**ので、
   手管理のファイルが増えるわけでもない
3. 上流への提案は、全面refactor(A)より**既定を変えないopt-in(A')**のほうが通りやすい。
   そして**A'を出すときも、shimで実際に動かした実績が最良の説明材料**になる
4. PR #3703が示すとおり、**上流の現在の慣行はベンダヘッダ側**。
   急いで逆向きの提案を出す理由が無い

残る気持ち悪さは「偽のベンダヘッダ」であること。
これはヘッダ冒頭に「これはWCHのSDKヘッダではない。TinyUSBが要求する4つだけを
満たすためにこのコアが生成したものだ」と明記することで、
少なくとも読み手の誤解は避けられる。

## 決定(2026-08-21、ユーザ指示)

- **まずBで出す**。shimを`variants/<SERIES>/`へ生成し、TinyUSBは無改造で使う
- **A'はずっと先**

### A'を先送りする理由(ユーザの指摘)

上流のstructを自前化するということは、**そのstructを誰かが保守し続ける**ということ。
そこには**健全なデータソース**が要る。手で写したstructを上流へ置けば、
新しい型番が出るたび、あるいは写し間違いが見つかるたびに、
上流に対して人力で追随する義務を負う。

したがってA'の前提は、**このプロジェクトのデータが育ち、
レジスタ定義がある程度自動で反映される状態になっていること**。
その信頼が無いうちに上流をrefactorしても、保守の当てが無い。

これは[R-20](register-map-data.ja.md)(レジスタマップに必要なデータ)を
「あると嬉しいもの」から**「上流貢献の前提条件」**へ格上げする話でもある。

### したがって今書くshimの位置づけ

今回のshimは**EVTを読んで手で起こしたもの**になる。
それはまさに上で「健全でない」と言っているデータソースそのものなので、
- shimは**このリポジトリの中だけの一時的な足場**として扱う
- 上流へ出す話は、R-20が形になってからにする
- shimのstructは**EVTとoffsetを突き合わせる自動チェック**を付けて、
  少なくとも「写し間違いは検出される」状態にしておく
