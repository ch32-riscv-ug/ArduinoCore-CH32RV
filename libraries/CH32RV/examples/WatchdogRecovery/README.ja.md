# WatchdogRecovery

[English](README.md)

アプリケーションが給餌を止めたとき、独立watchdogがチップをリセットすることを確認します。必要なのはUART接続だけです。

## 操作

1. リセット理由を読みます。このスケッチは起動時にwatchdogを自動開始しません。
2. `e`を送ります。`wdtEnable(2000)`が成功すると、`loop()`で`wdtFeed()`を続けるため動作を保ちます。
3. `x`を送ります。`loop()`は回しながら給餌だけを止めます。watchdogが満了すると再起動し、そのリセット理由を表示します。
4. 再起動後は再び`e`待ちに戻るので、リセットを繰り返さずに結果を確認できます。利用不可と表示された対象では、この実験は行えません。

## APIと改造時の注意

指定時間の単位はmsですが、実際の時間はwatchdog用clockとハードウェアの設定範囲に依存します。精密なタイマーとして使わないでください。一度開始したwatchdogを解除するAPIはありません。もう一度`e`を送っても停止せず、`x`の後は、この例では給餌の再開も行いません。

実際の用途では、監視したい処理が進んだことを確認してから給餌します。独立した周期割り込みから無条件に給餌すると、メイン処理の停止を見逃します。通常の処理やUART出力は、給餌に戻れる長さに抑えます。長い待ち処理を追加すると実験の意味が変わります。通常のRAM変数はリセットで初期化されるため、回復したい操作の状態は別途保存・復元する必要があります。

## 実行前の準備

ボードと正確なPart Numberを選び、スケッチの端子を回路図と照合します。ログはハードウェア`Serial`の115200 baud・8N1です。アダプタRXをボードTX、アダプタTXをボードRXへ接続し、GNDを共通にします。I/O電圧を合わせてください。基板のUSB端子だけでこのUARTが見えるとは限りません。

生成された`sketch.yaml`にビルドprofileがあります。ビルド成功は配線や実機動作の確認とは別です。[ビルド規則](../../../../docs/examples-build-rules.ja.md)と[書き込み経路](../../../../docs/upload-routes.ja.md)も参照してください。
