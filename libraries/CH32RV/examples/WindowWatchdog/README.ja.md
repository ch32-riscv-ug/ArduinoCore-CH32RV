# WindowWatchdog

[English](README.md)

窓ウォッチドッグは、餌が遅すぎるときだけでなく、早すぎるときにもチップをリセットします。このスケッチは操作で窓ウォッチドッグを開始し、窓の中で餌をやり、どちらの決まりも破れるようにしています。必要なのはUART接続だけです。

## 操作

1. リセット理由と、スケッチが選んだタイムアウトを読みます。40 msと`CH32RV.wwdgMaxTimeoutUs()`の短いほうで、後者はバスのクロックで決まります（48 MHzで約43 ms）。窓は半分の時刻で開きます。
2. `e`を送ります。`wwdgEnable(timeout, window, earlyWarning)`で開始し、`loop()`がタイムアウトの3/4（窓の中）で餌をやるので、動き続けます。
3. `x`を送ると餌が止まり、タイムアウトでリセットされます。次の起動で`window_watchdog`と、リセットの前に早期警告のコールバックが1回呼ばれたことを表示します。
4. または`f`を送ると、タイムアウトの1/8（窓が開く前）で餌をやるので、その餌でリセットされます。早期警告のコールバックは呼ばれません（0）。

`Window watchdog refused`と出たら、このクロックで設定できる範囲の外です。この実験は行えません。

## APIと改造時の注意

窓ウォッチドッグはAPBのクロック（PCLK1 / 4096 / 1〜8）を63カウントまでしか数えないので、タイムアウトは秒でなくミリ秒の単位です。長いものは`wdtEnable()`（独立ウォッチドッグ）を使います。両端とも1カウントの精度です。一度始めると止められず、早期警告も止められません。コールバックはリセットの1カウント前に割込みの中で呼ばれます。そこで餌をやれば動き続け、このスケッチのように理由を残すなら、起動で消さないRAM（`.noinit`）にチェック語と一緒に書きます。普通の変数はリセットで初期化されます。

決まった周期のタイマー割込みから餌をやると意味がなくなります。見張りたい処理が進んだところで餌をやります。餌と餌の間のUART出力や長い待ちは窓より十分短くします。このスケッチは動いている間は何も表示しません。`resetReason()`はこのリセット（`CH32RVResetReason::WindowWatchdog`）と独立ウォッチドッグのリセット（`CH32RVResetReason::Watchdog`）を区別します。

## 実行前の準備

ボードと正確なPart Numberを選びます。ログはハードウェア`Serial`の115200 baud・8N1です。アダプタRXをボードTX、アダプタTXをボードRXへ接続し、GNDを共通にします。I/O電圧を合わせてください。基板のUSB端子だけでこのUARTが見えるとは限りません。

生成された`sketch.yaml`にビルドprofileがあります。ビルド成功は配線や実機動作の確認とは別です。[ビルド規則](../../../../docs/examples-build-rules.ja.md)と[書き込み経路](../../../../docs/upload-routes.ja.md)も参照してください。
