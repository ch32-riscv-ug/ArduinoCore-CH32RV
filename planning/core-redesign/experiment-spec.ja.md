# コア再設計の比較実験仕様

P1 DESIGN-02、版 P1-1、2026-10-19。
[P0 の全体像](design-draft.ja.md)を、同等機能の比較・資源測定・変更課題で評価するための契約。
ここで固定するのは実験条件であり、製品 API や方式の採用ではない。
数値を指定した負荷・容量は実験用の入力で、実測値・チップの限界・製品の既定値ではない。

読む順序は、この仕様 → [用途と刺激](workloads.ja.md) → [実験の実行順](experiment-tasks.ja.md)。
最初の通常モデル向け作業は [EXP-00 の依頼](tasks/EXP-00/brief.ja.md)。
全体のフェーズとモデルを切り替える条件は [全体計画](../../CORE_REDESIGN_PLAN.ja.md)を正本とする。

## 比較群と固定条件

| 群 | 内容 | 比較での位置付け |
|---|---|---|
| U | 固定 commit の上流実装を元の想定条件で再現 | 利用例の成立と元の動作を調べる。機能差を残したまま A〜C の順位に入れない |
| R | 同じ用途契約を個別に直接実装した対照 | 共通実行器を持たず、必要な状態・失敗処理・同期は全て含める |
| A | 共通 I/O・データ部品＋明示 step | R に対する共通部品の費用と、B／C に対する進行管理の差を見る |
| B | 共通部品＋集約可能な work 予約 | 同じ用途状態を短い work で進める |
| C | 共通部品＋宛先 event | payload を必要とする message と集約通知を区別して配達する |

R と A は区別する。R でも同期・寿命・エラー処理を省かない。既存コア全体をリンクした R を「直接実装」と呼ばない。
R と A〜C の用途ロジック、入出力列、描画素材・数値形式は可能な範囲で共有し、異なるのは接続・進行と必要な管理情報にする。
候補に有利な実装だけ最適化しない。共通に適用できる修正は全群へ反映し、候補固有の工夫は別条件として記録する。

実験ごとに manifest へ source commit／dirty diff、新規ファイル hash、契約版、toolchain、全コマンド、
target・ABI・最適化、linker、clock、メモリ配置、容量、入力 trace、観測方法を固定する。
物理仕様や外部素材の数値を埋める作業も測定前に終える。変更後の結果は新しい条件 ID にし、旧条件と混ぜない。

### 基準と一条件ずつ変える比較

| 軸 | 基準条件 | 別条件として追加するもの |
|---|---|---|
| 通常実行 | 単一の通常 stack、ユーザー配達の再入なし、明示進行 | loop 外、delay、自動参加範囲、限定再入、独立 stack |
| I/O 結果 | 終端結果を回収まで保持。通常 queue の満杯で失わない | 完了枠の予約方式 |
| バス | 単一実行中 request、busy を返す。要求元は解放通知で再試行 | 固定容量 arbiter による待機受理 |
| 容量と配置 | 静的容量、heap なし、要求元が storage を所有 | 借用 storage、pool、実行時容量、動的割当 |
| 同期 | 通常処理専用と単一コア ISR 共有を別 build | 複数 producer、複数コア。別 backend と追加費用を記録 |
| 時間 | 必要時だけ接続。仮想時刻の期限判定と配達を分離 | tick／次期限方式、clock 変更、sleep、wrap |
| 診断 | サイズ測定は診断なし | trace・統計を有効化した別 build |

A〜C の基準は同じ起動機会で比較する。自動進行は別の便利さとして測り、A だけ進行機会を減らした比較を主結果にしない。
B は ready の仕事、C は受理した message／集約通知を処理する。snapshot と有限件数で一巡を区切り、
巡回開始位置を保存して未処理分へ公平に進む。実行中の再投稿は次の一巡へ持ち越す。
1対象1回を基準とし、件数上限を 1、4、8、対象数を 1、4、8 として独立に変える部品試験を置く。
これは処理時間の上限ではない。実行順や優先度を変える試験は追加条件にする。

## 正しさを判定する契約

契約 ID はテスト名ではなく観測する意味を表す。host、compile、実機の証拠は別列に残す。

| ID | 刺激と期待結果 |
|---|---|
| IO-01 | 受理／busy／不正／未対応を区別。受理した request だけが一度だけ終端になる |
| IO-02 | 完了前、cancel 要求後、通知保留中に buffer を再利用しようとする刺激。所有違反を検出し、hardware 停止・参照回収後にだけ再利用可能 |
| IO-03 | cancel と成功・失敗を両順序で発生。勝った終端結果を二重に書き換えず、回収は一度だけ |
| IO-04 | end と pending 通知が競合。破棄後の callback・古い世代への配達がない |
| DATA-01 | 空・満杯・wrap・部分操作。受理したデータを定義した順で取り出し、拒否したものを処理しない |
| DATA-02 | 通知消費／条件確認／登録／データ回収の各境界に producer を割り込ませる。必要な再実行を失わない |
| DATA-03 | semaphore 上限・二重返却、flag の any／all と clear、lock の owner、pool の二重解放を定義どおり扱う |
| RUN-01 | self-post と相互 post が続いても一巡から戻り、別の ready 対象へ進む。無限 callback 自体を中断する保証はしない |
| RUN-02 | loop・delay(0)・delay(n)・callback・setup・ISR ごとに、許可した範囲だけが進む |
| RUN-03 | producer が IRQ／通常処理／別コアの三種で待機。許可しない文脈は明示的に失敗し、暗黙の再帰や永久待ちを成功扱いしない |
| TIME-01 | 期限直前・一致・直後、周回、遅延後に期限到達を一度だけ通知。32 bit の相対期限指定は半周未満とし、範囲外指定は拒否 |
| TIME-02 | 周期を飛ばした場合、基準は最新の1回へ集約。回数通知・再基準化は別条件。時計の進行と handler の実行を区別 |
| STORE-01 | 容量・アラインメント・消去範囲・保護契約を満たす。中断後の読出結果が宣言した集合に入る |
| SLEEP-01 | 最終 idle 確認と休止の間に通知を発生。通知消失による眠り続けがなく、復帰後の時刻・I/O 状態が定義どおり |
| CORE-01 | 複数コアの所有・順序・可視性・返却・片側停止を検査。単一コア向けの割り込み禁止だけで共有保護を代用しない |

不正な使用を全て実行時診断する製品方針は採用しない。実験では計測用の owner／generation と canary を使い、
型や precondition による制約も区別して検証する。診断 build の費用を製品候補へ加算しない。
時刻幅、世代幅、寿命、再入、queue 順序を変える場合は別契約として結果を分ける。
32 bit の周回比較は、時刻を照合する間隔も半周未満の条件で検査する。
それを超える停止・休止は、広い時計、復帰時の再基準化、期限判定の保証外を明示する方式を別に比較する。
長期停止を検出できない時計に、周回回数まで推測させない。

## Host と実機の役割

host の独立した参照モデルは入力から期待状態を計算し、候補実装の出力を写して期待値にしない。
決定的な trace と境界への割り込み注入を優先し、seed 付きの追加乱数試験も失敗 trace を再生可能にする。
乱数試験は seed 0〜9、各10,000操作を初期条件とする。これは全 interleaving の証明ではない。

| 層 | 実行するもの | その結果で判断できないもの |
|---|---|---|
| host | 状態・順序・overflow・cancel・fake time・fault injection | MCU の時間、IRQ latency、Flash の実際の中断結果、cache coherency |
| compile/link | 対象 ABI での配置、未使用除去、symbols、生成命令、stack 解析情報 | 起動実行、計測 cycle、実周辺の動作 |
| 単一 MCU | 起動、割り込み・時間・転送の進行、実行時 RAM | 外部から見た通信の成立・電圧・消費電流 |
| 外部観測 | I2C peer、GPIO trace、PD source・電圧、電流計、電源断 | 未試験 part、別の接続相手、全負荷での保証 |

host C++ の意味検査には可能な範囲で sanitizer を使う。host の64 bit pointer や allocator のサイズを target RAM としない。
独立した参照結果、連番、受理数・回収数・拒否数・残数の保存則で、全件一致と「最新値だけ必要」を検査し分ける。

## Build と資源の測り方

EXP-00 は既存 probe の xPack GCC 14.3.0-1、`-Os`、LTO なしを変更せず再現する。
後続の比較は同じ toolchain を基準にし、`-Os` の LTO なし／ありを別条件で測る。
exceptions／RTTI／thread-safe statics を無効にする基準と、必要な機能が要求する差分を manifest に記す。
ABI・ISA は対象 part の資料から選ぶ。既存 probe の RV32E／RV32IMAC を全系列の実行適合性の証拠にしない。

LTO の archive は plugin 対応を確認し、GCC の `gcc-ar`／`gcc-ranlib` 等を用いる。
使用方法の根拠は [GCC 14.3 Optimize Options](https://gcc.gnu.org/onlinedocs/gcc-14.3.0/gcc/Optimize-Options.html)。
toolchain の版・配布 archive hash・関連する linker／binutils／libgcc も記録し、compiler driver の hash だけで環境全体を固定した扱いにしない。

| 指標 | 集計の定義 |
|---|---|
| Flash の配置量 | load image を領域ごとに集計。初期値付き RAM の Flash 側 image、alignment、vector、初期化表を含む |
| Flash の内訳 | code／rodata／初期値／配置間隙／保存予約／boot 等を分離。離れた領域を一つの巨大な bin 長だけで評価しない |
| 静的 RAM | `.data`、`.bss`、`.noinit`、TLS 等の実際の allocatable 領域。linker で予約した stack／heap／DMA 領域を分けて二重計上しない |
| 実行時 RAM | 各 stack の観測使用量、heap／pool の peak、未返却数。通常 stack と IRQ の同時利用・別 stack を明記 |
| 追加量 | 同じ target・flags・機能契約の baseline との差。負の値も保持し、比率だけで小さく見せない |
| 未使用費用 | header のみ、未参照 object、archive、無効登録、解除後を別にする。解除で静的 RAM が減るとは仮定しない |

最小 runtime、単独機能、独立した2機能、完成用途の4段階を測る。
未使用目標は追加 Flash・静的 RAM と実行時処理がゼロ。symbol と初期化・周期処理も確認し、
alignment で binary 差が相殺されたことだけを除去成功の根拠にしない。
ゼロを満たせない案は不都合も記録し、他の軸の結果とともに P5 へ渡す。

`-fstack-usage` は関数ごとの情報であり、呼び出し列・IRQ の重なり・間接呼び出しは別に調べる。
[GCC 14.3 Developer Options](https://gcc.gnu.org/onlinedocs/gcc-14.3.0/gcc/Developer-Options.html)の static／dynamic／bounded を保持する。
canary と最小 SP の観測を補助にし、観測 peak を必要量の証明と呼ばない。
LTO 後の命令と測定 firmware が一致しない場合、その差を未確定要因にする。

### 予算候補

一律に「RTOS は何 KB 以下」とは置かず、次の三つを全候補へ適用する。

| 予算 | 条件と使い方 |
|---|---|
| B0 未使用 | 任意部品の追加費用ゼロを目標。実際の除去条件と満たさない構成を記録 |
| B1 完成用途が収まる | `Flash image + 保存予約 + boot等の予約 ≤ そのpartの該当Flash領域の総容量`。RAM は静的使用＋stack 予算＋heap/pool 予算が各配置領域に収まる。予約を上限から差し引いた場合は左辺へ二重加算しない |
| B2 具体的な変更も収まる | Knob の設定2件化、X035 のタッチ追加、保存1消去単位の追加等を実装し、B1 と同じ式で残容量を見る |

V003 の公称16 KB Flash・2 KB SRAM は [WCH の概要](https://github.com/openwch/ch32v003)に記載される。
X035 の公称62 KB Flash・20 KB SRAM は [WCH の概要](https://github.com/openwch/ch32x035)に記載される。
実験では正確な part・memory map・予約・配置を資料で照合して byte に確定する。概要値をそのまま sketch 上限にしない。
V006 と H417 は領域ごとの確認を先に行い、RAM 総量だけで共通 buffer の配置可否を判断しない。

stack 予算は P2 の対照実装の呼び出し構造、IRQ 方針、解析不能な経路を確認して測定開始前に記録する。
説明できる上限が得られない場合は「観測上収まる」と「予算を確認済み」を分ける。
余裕が不足する候補だけに小さい入力や buffer を与えない。予算変更は全候補を同条件で再評価する。
B2 の用途追加は将来用の空 RAM を常設する指定ではなく、具体的に残せる余地の比較である。

## 時間と負荷の測り方

時間計測では、source timestamp → 通知受理 → handler 開始 → I/O 開始 → 完了 → 結果回収を分ける。
観測 interval を `end - start` と定義し、同じ時計か、外部計測との同期誤差が分かる組で計算する。
IRQ 禁止区間と handler の実行時間を混同しない。GPIO marker の命令・ログ採取・timer 読み出しの費用を空操作で測る。
補正前を保存し、補正後は方法と誤差を添える。host の処理時間を MCU cycle に換算しない。

部品の初期測定は100回の warm-up 後に10,000回、独立した5 run とする。
完成用途は決定的 trace を1 run とし、実機の通常負荷は60秒を5 run、burst と故障 trace は各5 run とする。
この長さは初期比較の窓であり、長期耐久性の基準ではない。計測器や相手の制約で変更するときは全候補同条件にする。
run 内の min／median／p95／p99／max と件数、run 間の幅、受理・拒否・欠落・期限超過を残す。
分位点は昇順の `ceil(p*n)` 番目とし、少数標本ではその旨を表示する。未完了要求を遅延統計から黙って除外しない。

長いユーザー処理は 0、1、10、100 ms 相当の負荷を注入し、途中の進行呼び出しなし／分割して呼ぶ条件を分ける。
実機の時間源で負荷を較正し、回数だけから ms を推定しない。PD を失う条件があっても記録し、
外部 protocol の必須条件と用途の操作感を別に判定する。遅延を理由に WDT reset を自動で入れない。

## 判断と記録

| 状態 | 意味と次の扱い |
|---|---|
| 成立 | 指定契約を通過。測定値と条件を付ける |
| 契約不成立 | 二重完了・破損・失われる必要通知等。通常担当で実装修正し、契約変更が必要なら高位判断へ戻す |
| 容量不足 | 同じ条件で fit しない。サイズ・不足量を記録し、他の測定をゼロにしない |
| 未検証 | 設備・資料・実装の不足を理由別に記録。採用の根拠にはしない |
| 対象外 | hardware 能力や明示した実験範囲によるもの。失敗を後から対象外に変更しない |

数値比較では、正しさと B1 を確認した上で Flash・RAM・処理費用・使い方の負担を並べる。
小さい用途で不利でも複合用途で有利になる案、容量と理解しやすさが競合する案を残し、根拠のない合算スコアを作らない。
最適化・サイズ差が計測条件の揺れに埋もれる場合は優劣不明とする。
費用が低く、変更課題・必要な能力でも劣らない案があれば、その範囲で候補を減らせる。
最終的な共通化範囲、系列別構成、公開 API は P5 で選ぶ。

結果は `contract × target × candidate × profile × run` ごとに保存する。
JSON／CSV の結果には単位と null の理由を付け、Git 管理する result に短い表、コマンド、生成物 hash、
再取得・再生成方法、差分、未検証を記す。生ログ・ELF 等は一意な `work/` 下とし、別セッションへ渡す archive を識別できるようにする。
この仕様に従う新しい試作は既存コアの実装を選定条件にしない。設備操作は [既存の試験規則](../../tests/README.ja.md)に従う。
