# レビュー02・利用者レビュー03への応答と提案版3

2026-10-22。[レビュー02](review-02.ja.md)と[利用者レビュー03の整理](review-03.ja.md)への提案者応答。
対象は版2（`f076a8e`）。[proposal](proposal.ja.md)と[usage](usage.ja.md)は版3へ更新した。
**推奨の変更であり、利用者の最終承認、版3の第三者レビュー完了、製品仕様の採用ではない。**

## 全体判断

推奨を **A＋S（共通部品＋明示step、自動進行はsystemだけ）** へ変更する。
Bは最終構成の任意部品として接続境界を残すが、基本教材・標準用途の前提から外す。
版2でも基本教材はAだったが、版3では全体の優先案もAへ変え、userの自動配達を標準範囲から外す。
これはAで作って後からBへ置き換える計画ではなく、Aを中心に単独部品と任意executorを最初から分離する設計。

レビュー02は版2に構造を止める矛盾がないと評価した。レビュー03はその構成が用途・理解の負担に見合わないと評価した。
両者は矛盾しない。元のR1に定めた「Bの接続が定型負担を減らさなければA中心／S限定へ」の判断材料が得られた。
ただし一つの開発セッションの意見で、全利用者の学習効果を確定しない。

## 今選ぶ二つの軸

| 軸 | 版3の推奨 | 失う便利さ／再検討条件 |
|---|---|---|
| user処理の組み立て | Aの直接step＋単独Deadline／Period。Bは任意 | 不要なstep確認は残る。休止調停・起動条件集約が具体的に負担を減らす用途でBを評価する |
| 自動で実行する範囲 | S限定。beginで内部systemを登録し、user関数は明示run／配達呼出しだけ | delay中にuser callbackが自動進行する便利さを失う。明示配達では成立しない具体用途があれば、構造確定前に比較し直す |

S限定でもISRは禁止、dispatch中は非再入という文脈規則は残る。すべてのdelayが同じ処理になるとは言わない。
delay(n>0)はcallback内でも時間を待つため、「callback内では何もしない」はdelay(0)に限る。
通常loop／setupのdelayからsystem状態・受信bufferが変わることは残る。systemという名で任意user関数を呼ばないことが条件。

## 指摘への応答

| 指摘 | 提案への反映／残す範囲 |
|---|---|
| 02 N1 busy wait | 採用。照会だけのspinは通常serviceを進めない例を教材へ追加。IRQだけで完了する操作まで必ず停止するとは一般化しない。最後のservice時刻等を任意診断の候補とし、止まった通常文脈自身がその場で警告できるとは約束しない |
| 02 N2 登録storage | 固定配列とintrusive方式をR2の限定比較に残す。登録成功の意味を共通にし、枠不足は枠がある方式だけの失敗とする。node費用はpointer一本と固定しない。寿命・削除中走査・ready状態・整列・owner等を含む総費用で比較 |
| 02 N3 AfterSetupAuto | 版2の曖昧さの指摘は妥当。版3はuser自動参加自体を外すので当該modeも除く。版2への指摘が最初から無かった扱いにはしない |
| 03 U1〜U3 | A中心へ変更。K0からB併記を外し、X0のBは任意比較として後ろへ置く。条件検査と通知接続の二重保守をBの費用として扱う |
| 03 U4 | B不使用時の依存・容量除去を必須の確認条件にする。ただし模型の数値をOEPに加算しない。OEP報告を新たな必須port実験へ拡大しない |
| 03 U5 | S限定を推奨。userのExplicitOnly／AutoEligible／AfterSetupAutoとruntime参加操作を標準案から除く。libraryのuser callbackも明示配達 |
| 03 U6 | 任意Bはattach成功で初回ready、実行は次の明示run。期限接続はexecutorへ一操作で登録する疑似形へ。接続完了前にrunしない。容量・解除等の契約は省略しない |
| 03 U7 | wake通知と結果ownerを分けて表記。bus availableは再試行のhintで予約権ではなく、結果takeは要求の単一ownerのみ |
| 03 U8 | 採用。ManualServiceは上級の依存除去・明示進行構成。既定はbeginで自動 |
| 03 U9 | 採用。時刻値と期限状態だけを持つ部品をAに示す。中央timer表・登録・callbackは不要。時刻源自体の費用や不連続処理は残る |

## 推論を限定する点

- Aで誤ると常にCPUの無駄だけになるわけではない。状態判定・期限・回収を誤れば停止や誤処理も起きる。
  Bに固有の追加リスクは、状態は正しくても起動経路の不足で実行されないこと。
- 63,488 − 62,568 = 920 Bは報告値の算術として整合する。ただしB増分の既存表はRV32E・LTOなしのlogic probe。
  X035 OEPの実増分・fitを示さない。Bをこの用途で選ばないという判断は尊重し、数値による不可能証明とは区別する。
- OEPのbit-bang中にUSBが成立するという報告は参考用途であり、任意長のIRQ禁止やPDの時間条件を保証しない。
- ready集合も計測口もBだけでしか得られない能力ではない。Aでも用途が状態を集約できる。Bは共通の接続・調停としてまとめる費用と便益を比較する。
- 全work走査は負荷・呼出し時刻自体を変える。症状の差は接続漏れの手掛かりであり、診断の完全性や低費用は未検証。

## 次の順序

1. 版3のA中心とS限定を一体の優先案として利用者が選ぶ。変更点に限って再レビューできる資料を渡す。
2. 選択を変え得る不足だけR1〜R4へ渡す。既存R1には用途評価1件を記録し、挙動予測・初学者評価まで完了とはしない。
3. 通常モデルへ渡す実験は、選んだ仕様・比較条件・失敗時に戻す判断を固定してから行う。OEP port、電池用途、全work診断を別々の先行必須案件へ増やさない。
4. 必要な根拠が揃った段階で高位の構造確定へ戻し、その後に製品実装する。
