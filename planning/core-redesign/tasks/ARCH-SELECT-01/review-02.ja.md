## 新たに見つけた点（いずれも公開前。構造は変えない）

### N1 delay を挟まない busy wait は何も進まない

- 対象：G2、Q3。proposal「照会は状態を読み…裏で汎用 poll を行わない」、usage「setup の system 進行」。
- 根拠：論理。照会を観測だけにした帰結として、`while (!usb.ready()) {}` のように delay を挟まない spin は、AfterLoop hook にも delay にも到達しないので永久に進まない。Arduino では `while (!Serial);` という書き方が広く使われている。
- 修正案：契約はこのままでよい。教材と診断で扱う。(a) 基本例は必ず `delay()` を挟む形で示す。(b) 任意診断に「一定時間 service が一度も進んでいない」を観測できる口を置く（F11 の計測口の応用。常設しない）。(c) `ready()` に進行を持たせる対案は採らない（F2 の選択と矛盾する）。
- 追加検証：不要。R1 の読み合わせに「delay の無い spin」を 1 行足す。

### N2 登録枠の容量を利用者に見せない作りを選べる

- 対象：G2、F10。proposal「固定容量の登録枠不足等は明示失敗にし」。
- 根拠：論理。登録枠を runtime 側の固定配列にすると、ライブラリの `begin()` が「利用者が runtime の容量を小さく書いたから」失敗する新しい失敗が生まれる。Arduino の利用者は runtime の容量を知らない。
- 修正案：登録を intrusive（各 driver が自分の list node を 1 つ持つ）にすれば、枠は存在せず、枠不足の失敗も消える。費用は driver ごとに pointer 1 本で、runtime 側に配列も容量も要らない。「登録枠不足は明示失敗」はその場合は不要になり、残る begin の失敗は hardware／owner／再 begin の意味だけになる。固定配列を選ぶなら、既定容量の決め方（linker で数える、系列ごとの上限）を公開前に定める。
- 影響：R2 の「ManualService の依存除去」と同じ試作で、intrusive node の費用も測れる。
- 追加検証：R2 に 1 条件（intrusive／固定配列）。結果で選ぶのは実装方式だけで、契約は変わらない。

### N3 AfterSetupAuto の callback 登録は「user の自動参加」そのもの

- 対象：G2、F8。proposal「userの登録と自動参加は別操作にする」と「登録時にExplicitOnly／AfterSetupAuto等の配達方針を指定」。
- 根拠：論理。受信 lambda を AfterSetupAuto で登録した利用者は、それだけで loop 中の `delay()` から user コードが走ることを選んだことになる。これは G2 の「明示的に自動参加した user work」と同じ性質で、別物のように読める記述は誤解を生む。
- 修正案：「配達方針 AfterSetupAuto の指定は、その callback の自動参加の明示である」と一文書く。G2 表の「明示的に自動参加したuser work」に callback も含むことを明記。
- 追加検証：不要。

## 判断

- レビュー 01 の指摘は版2 でいずれも解消、または正しく訂正された。構造確定を止める項目は残らない。

- 利用者の最終選択に進んでよい。選択後の検証は R1〜R4 の記載範囲でよく、N1〜N3 のために新しい実験は要らない（N2 は R2 に 1 条件）。
- 版2 の usage に対する R1（第三者の予測）は未実施。レビュー提出者が自分の提案を読み合わせても R1 の代わりにならないので、別の読者が要る。
