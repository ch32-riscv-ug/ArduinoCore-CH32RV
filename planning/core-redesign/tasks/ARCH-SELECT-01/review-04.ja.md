## 新たに見つけた点（公開前。構造は変えない）

### V1 ホストが待っている「データ提供」の callback は、S 限定の例外として区分が要る

- 対象：G2、G4、03 U5。proposal「ライブラリの受信callback等もuser処理に分類し、明示run／配達呼出しでのみ実行する」。
- 重大度：**公開前に解決**。利用者の判断が要る。
- 根拠：観測事実＋論理。
  - USB のクラスには、ホストが応答をタイムアウト付きで待つ段で**利用者のコードがデータの出どころになる**ものがある。MSC のブロック読み書き（利用者の `read/write` provider）、HID の GET_REPORT／SET_REPORT、vendor の control IN／OUT、CCID の APDU、DFU の block。製品コアはこれらを `ch32rv_usb_task`（delay／loop の戻り）から利用者の provider を呼んで答えている。
  - 版3 の S 限定を文字どおり適用すると、これらは `deliverUserOnce()` が呼ばれるまで答えられない。`loop()` に `delay(500)` がある普通のスケッチでは MSC が 1 ブロック／500 ms になり、`while (!usb.ready()) delay(10);` の最中にホストが始める INQUIRY／READ CAPACITY には答えられない（列挙直後、setup を抜ける前に来る）。失敗ではなく性能と到達性の問題だが、「USB メモリの速さが loop の delay で決まる」という隠れた依存になり、製品コアからの後退になる。
  - 一方で「受信したよ」という**通知**（CDC の onRx 等）は S 限定でよい。受信データは有限 buffer に残り、`read()` でも `deliverUserOnce()` でも取れる。問題は通知ではなく provider。
- 最小の反例：
  ```cpp
  usb.msc.setProvider(myBlocks);          // ブロックの出どころは利用者
  void setup() { usb.begin(); while (!usb.ready()) delay(10); }   // この間にホストが READ を出す
  void loop()  { blink(); delay(500); usb.deliverUserOnce(); }    // 1 ブロック / 500 ms
  ```
- 修正案（どれかを選ぶ。レビュー提出者は (a) を推す）：
  - (a) G2 に「**provider**」の区分を足す。「ホストが待つ protocol の段でデータの出どころになる利用者関数は、そのクラスに明示的に設定（`setProvider`）されたときに限り、system の進行の中から呼ばれる。本体は dispatch 中の規則（再入しない、delay(0) で yield しない、短く返す）に従う。通知（onRx 等）は provider ではなく、明示配達のまま」。版2 の F8 で退けた「許可の継承」とは違い、登録した時点で呼ばれる場所が決まる明示の選択で、対象はデータ提供に限る。
  - (b) provider を持つクラス（MSC、HID の report、vendor control、CCID、DFU）は A＋S の標準範囲から外し、「system 側の storage（RAM disk、固定 report）で答えるものだけ」を標準にする。利用者コードを provider にしたい人は任意部品。
  - (c) S 限定のまま、`deliverUserOnce()` を一定間隔以下で呼ぶことを利用者の責任にし、教材に書く。
- 影響：(a) なら G4 の USB クラスの表に provider の列が要る。(b) なら製品コアの MSC／CCID／DFU の使い方が変わる。(c) は到達性の問題を解かない。
- 追加検証：不要。契約の選択。R1 に「MSC の provider がいつ呼ばれるか」を 1 行足す。OEP の probe が vendor の control 要求に利用者コードで答えているなら、現行コアでは system 配達で動いている実例なので、版3 の S 限定でどうなるかを OEP 側で読み合わせてもらうとよい。

### V2 ライブラリごとの配達 API は、呼び忘れの場所を増やす

- 対象：G2、03 U5／U6。usage の `usb.deliverUserOnce()`。
- 重大度：公開前に解決。
- 根拠：論理。利用者の第一の希望（F10）は「呼び忘れると更新されない処理を無くす」こと。S 限定で `maintain()` の呼び忘れは消えるが、ライブラリごとに `usb.deliverUserOnce()`、`pd.deliverUserOnce()`、`net.deliverUserOnce()` と増えると、呼び忘れの場所がそのぶん増える。レビュー 03 の U6「登録手順が多い」と同じ種類の負担。
- 修正案：user の配達も**一つの明示呼出し**にまとめる。`runtime.deliverUser()`（または user 用 executor の `runOnce()`）が、登録済みの user 配達を有限件数まとめて行う。S 限定は保つ（delay／AfterLoop からは呼ばれない）。ライブラリごとの API は残してもよいが、教材はまとめた呼出し 1 行にする。
- 影響：G2 の「明示 run・配達 API」の行に「まとめて呼べること」を足す。費用は登録一覧（F10 で既にある）を user 側にも持つだけ。
- 追加検証：不要。

## 利用者の判断に関わる注意

- 版3 は、レビュー 03（OEP）の「用途・読解の負担」を受けて user の自動配達を外した。レビュー提出者もその方向を勧めたので支持する。ただし利用者（本人）が述べた優先事項は「呼び忘れで動かないことを無くす」で、版3 はそれを **driver の進行については満たし、利用者の callback については満たさない**（応答文も「失う便利さ」として挙げている）。違いは、呼び忘れたときの見え方：版3 では protocol が死ぬのではなく、データが buffer に残って `read()` で取れる。この「失敗が見える形で残る」ことを受け入れるかが、利用者の選択。
- V1 は、その選択のうち「ホストが待つ段」だけを切り出したもの。ここだけは buffer に残しておけない（ホスト側が待ち切れない）ので、別に決める必要がある。

## 判断

- 版3 は内部で一貫しており、レビュー 01／02 の指摘は引き継がれている。構造確定を止める項目はない。
- 利用者が選ぶのは、(1) A＋S（版3）、(2) V1 の provider の扱い (a)／(b)／(c)、(3) V2 のまとめた配達呼出し。(1) はレビュー提出者も支持。(2) は (a) を勧める。
- R1 は未実施のまま。レビュー 03 は用途評価 1 件で、盲検の予測ではない。V1 の 1 行を足したうえで、別の読者に usage を渡す。
