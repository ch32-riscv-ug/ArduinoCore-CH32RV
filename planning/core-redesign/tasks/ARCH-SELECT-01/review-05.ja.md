# 第三者レビュー回答 05：提案版 4（限定 provider と一括配達）の確認

2026-10-22。[レビュー 04](review-04.ja.md)の提出者による、[応答](review-04-response.ja.md)と提案版 4
（[proposal](proposal.ja.md)、[usage](usage.ja.md)、commit be0ecea）の確認。レビューであり、採用決定ではない。

```text
レビュー対象版／commit：be0ecea（提案版4）。版3 ac0071b との差分と応答文を読んだ。
レビュー者・独立性：レビュー 01〜04 と同じ。
推す全体案：版4 の形（A を基本、system は begin で自動登録、通常の通知と work は明示呼出し、
  専用登録した protocol provider だけ system 中で同期呼出し、通知の配達は共通入口で一回）。
全体評価：妥当。レビュー 04 の V1／V2 は解消。構造確定を止める指摘も、公開前に足すべき契約もない。
  残るのは利用者の選択と R1〜R4。
```

## 確認したこと

| 点 | 確認結果 |
|---|---|
| V1 provider | (a) を限定して採用。「専用 API で登録」「begin 前に本体と state を初期化」「begin 成功後の system 文脈で同期呼出し」「IRQ・他 core へ移さない」「run／配達へ再入しない、delay で待たない、spin しない」「未準備／失敗を返せる」「借用と寿命は G3」「通知を inline 配達しない」「end は参照排出後」。レビュー 04 で挙げた条件をすべて含み、さらに「onRx を provider に昇格させない」「クラス名で自動分類しない」で範囲が閉じている。妥当 |
| V1 の事実の訂正 | 製品コアの HID GET_REPORT は未処理として拒否、MSC の inquiry／capacity は保持済み情報で答える、という応答の指摘は正しい。レビュー 04 の「列挙した全要求が利用者の provider を呼ぶ」は言い過ぎで、provider が要るのは MSC の read10／write10 のような媒体操作と、動的な応答生成に限る。版4 の切分け表はその区別になっている。「1 block／500 ms」も例示であって測定値ではない |
| V2 一括配達 | 採用。通知の登録成功に共通配達元への接続を含め、`runtime.deliverUserOnce()` 一回で有限に巡回。delay／AfterLoop からは呼ばない。個別配達と共通配達が同じ通知状態を消費して二重消費しない、という規則も入った。妥当 |
| 版3 との関係 | 「provider を使うと delay 中に利用者の関数が動く」ことを例外として明記し、版3 の厳密な S 限定からの変更だと書いている。黙って戻していない |
| R1〜R4 | provider と通常通知の区別、setup 中の provider、共通／個別配達の二重消費、provider 内の run 抑止が足された。妥当 |

## 補足（指摘ではない）

- 版4 の provider 例外は、レビュー 03（OEP）が求めた「user 関数を自動で呼ばない」からの部分的な変更。OEP 側がこの例外を見ていないなら、最終選択の前に版4 を渡すのがよい。
- usage の `updateReportWithoutYield(report); delay(10);` の形は、レビュー 01 の Q3 で述べた「delay() は yield 点で、共有 state はそこで整っていること」をそのまま教材にしている。provider を使う人に最初に教えることはこれ一つで足りる。

## 判断

- 利用者が選ぶのは、応答文のとおり「A 中心の維持、(a) の限定 provider 例外、任意の一括明示配達」の一体。レビュー提出者は三つとも支持する。
- 選択後は R1（別の読者による usage の予測）が先。新しい実験は要らない。
- 製品コアへの反映は、選択と R1〜R4 の該当範囲のあとに行う。それまで製品 API を変えないという方針に同意する。
