# 第三者レビュー依頼：CH32RVの全体構成選択

状態：2026-10-22、依頼資料作成済み。**レビューは未実施、決定は未承認**。
レビュー先への送信は行っていない。別セッション・別の設計者へ渡せる資料として用意した。

## 依頼

小型CH32を中心に、ノンブロッキングな処理分割と資源の見通しを重視するArduino Coreを検討しています。
既存実装との互換・移行コストは制約にせず、最終型と拡張境界を選んでから本実装します。
A（共通部品＋明示step）、B（短いworkの予約）、C（宛先event）、別stack／RTOSを比較し、Bを任意に組み込む案を推奨しています。

**推奨案を承認するためのレビューではありません。Aへの変更、scopeの縮小、構造の棄却も同じように検討してください。**
モデル名・試験件数・資料量を設計の正しさの根拠にしないでください。
追加実験は、結果で何を選び直すのか示せるものだけ提案してください。

## 読む順序

1. [選択案](proposal.ja.md)：比較、数値と限界、G1〜G5の推奨、反対理由。
2. [利用者コードと状態](usage.ja.md)：K0／X0、進行場所と失敗時の意味。
3. 疑問に関係する選択案の出典。全実験履歴の読破は前提にしない。

過去のresult末尾の「次は」は旧計画です。現在の実行範囲は[判断中心の計画](../../decision-focus.ja.md)。
疑似コードは設計案であり実装・実測ではありません。host模型・断片link・実機・人の評価を分けて判断してください。

## 特に反証してほしい問い

| ID | 問い | 回答に必要な具体性 |
|---|---|---|
| Q1 | Bの便利さは、Aのstep列より価値があるか | K0／X0の具体的な記述・変更で比較。抽象的な「拡張性」だけで支持しない |
| Q2 | 下位部品単独とwork接続を同じ契約で維持できるか | 二重進行、通知登録と条件確認、生成依存・固定RAMの問題を指摘 |
| Q3 | system＋明示参加userの自動進行は妥当か | loop→delayでの介入、callback非再入、setup、別executor経由の再入を追う。S限定／完全明示と比較 |
| Q4 | 所有・取消・終端・回収・解除は一貫するか | 最小の操作順で矛盾を示す。停止宣言だけで実停止を仮定していないか |
| Q5 | queue等の公開範囲と待機制限は十分か | semaphoreとmutex、即時操作と待機、ISRとcore間の差を確認。必要な用途が書けないなら例示 |
| Q6 | 保存・休止・H417・外部RTOSの境界は後の変更を防げるか | callbackのowner、時刻不連続、停止中の保持、shared／localのどこが不足か |
| Q7 | 数値からの推論が過剰ではないか | 同等条件か、stackやstartupを除いたまま全体費用を主張していないか、未測定の便利さを混ぜていないか |
| Q8 | 今決めるものと後段化の区切りは適切か | 基礎契約を変え得る未検証だけを列挙。全条件の網羅を要求しない |

## 回答様式

```text
レビュー対象版／commit：
レビュー者・独立性（同じ案の作成へ関与したか）：
推す全体案：A／B／C／別stack／その他（根拠付き）
全体評価：妥当／条件付き妥当／再設計が必要／材料不足

指摘ごとに：
- ID、対象G・Q、文書の該当箇所
- 重大度：構造確定を止める／公開前に解決／後段の改善
- 根拠：観測事実／論理上の反例／好み・仮説（区別する）
- 最小の反例または具体的な利用コード
- 修正案と、他の責務へ及ぶ影響
- 追加検証が要る場合：結果Aなら何を選び、結果Bなら何を選ぶか

指摘しなかった主要前提、レビューできなかった範囲：
```

コードへの好みだけで採否を決めず、状態・実行機会・資源費用・学習上の問題へ結び付けてください。
指摘がないことを実機性能や教育効果の検証済みとはしません。

## レビュー後の決め方

1. 指摘を「構造上の矛盾」「選択の好み・負担」「物理／測定不足」に分け、提案者の応答と未解決を残す。
2. 資料と論理で解ける指摘はその場で反映する。実験が必要ならR1〜R4の該当する最小範囲だけへ渡す。
3. 選択を変えた場合はG1〜G5とK0／X0を一体で更新する。局所修正で異なる再入・寿命規則を増やさない。
4. 利用者がレビューと応答を見て最終選択する。未解決の構造上の矛盾・物理依存は明示し、必要な検証を経てP5後半で確定する。
5. その後に採用記録・公開契約・P6依頼へ反映する。採用しなかった候補と再検討条件も残す。
