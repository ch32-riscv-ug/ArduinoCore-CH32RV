## 設計から得た問い

以下は性能を観測した事実ではなく、状態と所有を具体化して得た設計上の論点。

1. 最新状態の通知と、全件保持するデータを分ければ、全変化を payload event にする必要はない。
   ただし集約・競合防止・再起動条件の実装費用を含めて比較する必要がある。
2. 完了を失うと資源を回収できないため、通常 queue の満杯とは独立して結果を保持・回収できる経路が必要。
   sticky な結果と予約した配達枠のどちらが小さいかは未測定。
3. 単一 stack・非再入の callback は、一回の処理を返す必要がある。
   `delay(0)` による進行は呼び出し文脈で意味が変わるため、費用だけでなく利用者の理解も確認する。
4. system 用の容量を分けても、同一コア上の長い通常処理から独立した時刻保証にはならない。
   PD 等は hardware／IRQ／通常処理の分担と外部条件を別に検査する。
5. PPS UI では desired／inFlight／confirmed と接続の寿命が必要になる。
   実行方式の違いでこの用途の意味まで変えて比較しない。

## 次の作業：DESIGN-02／P1

引き続き高位モデルで、[計画の P1](../../../../CORE_REDESIGN_PLAN.ja.md#p1-で定義する比較契約)を具体化する。

1. D01〜D12 と EXP-00〜06 の対応を作り、各実験で変わる判断を記す。
2. V003 と X035 の観測可能な機能、容量・入力・失敗条件を定める。上流・同等機能の直接実装・候補の差を分ける。
3. A〜C の基準と一条件ずつ変える比較を定める。独立 stack の対照が必要な問いと範囲も決める。
4. 起動・未使用・追加費用・完成用途、正しさ・処理費用・教材を分けて測定方法と予算候補を作る。
5. 物理調査と実機が必要な項目を特定する。設備未確定でも実行可能な host／compile 作業を明示する。
6. 通常モデル向けの EXP-00 作業依頼を作成し、依存する後続実験の開始条件を記す。

P1 が終わるまでは、A〜C の採用、API 名や stack 数、delay の動作を公開仕様として固定しない。

最終仕様を選ぶ P5 または重大な前提変更で高位モデルへ戻す。
