# I2Cの小分け処理とbuffer寿命を考える課題

2026-10-20。公開APIを決める前の教材素材。人が実際に予測・変更できたかは未評価。
[測定結果](i2c-master-result.ja.md)と実験用`i2c_master.hpp`を使う。
このclassの単体入口は、clock・pin設定済み、周辺を排他的に所有し、IRQが介入しない条件を要求する。
このまま完成したArduino用サンプルとして配布するものではない。

## 画面を更新しながら別の仕事を進める

X035でPDの状態、ボタン入力、I2C表示を扱う場面を考える。
この課題は表示側のI2C要求を短く進める練習であり、PDの実処理や期限成立はまだ接続していない。

1. 表示に使うbyte列を用意し、要求を1回だけ受理してもらう。
2. 呼出し機会ごとに`step()`を1回呼び、その前後でボタンや別の有限処理を進める。
3. 完了通知を観測する。通知の確認・解除と、bufferの回収は別の操作として扱う。
4. `take(token, completion)`が成功してから次の表示データへ書き換える。

`step()`が戻ることと、要求全体が終わることを分ける。
相手が進まなければ何回呼んでも完了しない。短い関数へ分割するだけでは通信の時間保証は生まれない。
長い描画計算を入れると、その間はこのpolling方式の通信も進められない。
常設task、timer割り込み、callbackの自動配信はこの実験にはない。

## 操作の前に結果を予測する

| 場面 | 予測すること |
|---|---|
| 受理直後に表示bufferを書き換える | 保護付きでは拒否されるか。raw側の利用者には何の約束が必要か |
| `cancel(token)`が成功する | すぐbufferを書き換えてよいか。停止待ち中に誰がbufferを所有するか |
| readのADDR処理後に取消を要求する | 取消要求が成功しても、受信成功で終わる場合があるか |
| `ack(token)`で完了通知を消す | bufferも返却されるか。次の要求を受理できるか |
| 稼働中に`end()`を呼ぶ | 完了通知、進行、回収、再openのうち何が許可されるか |
| NACKなどでwriteが失敗する | DATARへ書いた数、BTFを観測した数、相手が実際に反映した数を区別できるか |
| STOP待ちが終わらない | timeout通知だけでbufferを返してよいか。回復と回収の証拠は何か |

回答の照合には次を使う。

```sh
uv run --project tests --locked pytest -c tests/pyproject.toml \
  tests/unit/core_redesign/test_i2c_master.py -q
```

取消は要求であり、停止・回収の完了ではない。readは規定の受信手順を最後まで進めて成功する場合がある。
通知を解除してもbuffer貸出は残り、`take`が回収する。`end`後も回収まで進行と寿命を維持する。
writeの`confirmed`はBTFを観測できたprefixであり、失敗時の相手機器の副作用を完全には表さない。
STOPや受信状態を解消した証拠がなければ、timeoutを報告するだけでは再利用可能にならない。

## 容量と仕組みの費用を比べる

8 byteから32 byteへ増やし、Flashと静的RAMの変化を先に予測する。
rawと保護付きの比較は同じ状態機械・同じ要求内容で行うが、利用者の書換えを拒否する能力は異なる。
rawの貸出規則を破った使い方まで、同等の安全性があると解釈しない。

`--suite i2c-master`のCSVで差を確認し、payload容量、owner情報、要求状態、測定入口の変数を分けて説明する。
空構成と、宣言しただけの未使用構成も比較する。未使用0 Bは、そのlink条件で確認した結果である。
Flash容量の増減がbyte数に比例するとは限らず、最適化や分岐の配置も変わる。
`.su`の関数frameを合計せずにpeakと呼ぶこともしない。
