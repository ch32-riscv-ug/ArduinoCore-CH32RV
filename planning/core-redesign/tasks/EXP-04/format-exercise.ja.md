# 保存形式の容量と更新途中を予測する課題

2026-10-20。小型MCUで容量と保護を分けて考える教材素材。
[比較結果と条件](format-result.ja.md)を使う。実機での電断耐性や教育効果の評価は未実施。

## 1ページで何を残せるか

V003のfast modeで、設定8 B、program／erase単位64 Bを使う。
次を実行する前に、必要な予約量を予測する。

1. 既知長8 Bを消去して書き直す。
2. 16 Bのheaderを付け、CRCで不正を検出する。
3. 更新中も前の版を残すため、同じ大きさのbankを2つ使う。
4. 内容12 Bの完了印を、bodyとは別のprogram単位へ最後に書く。

「設定8 B＋header16 B＋完了印12 B＝36 Bなので1ページで足りる」という計算の前提を点検する。
今回の媒体模型は消去後のprogram単位へ一度だけ試みるため、完了印には別の64 Bを割り当てる。
同じページへの再programが許される物理条件を確認するまで、後から印だけを書き足せると考えない。
この制限は実験条件であり、全CH32の物理仕様を確定するものではない。

## 操作の途中で止める

比較模型はbegin後、stepを呼ぶたびにeraseかprogramを1回行う。
自動taskやdelay内で更新を進める仕組みはない。

| 止まる位置 | 予測すること |
|---|---|
| 上書きする領域のerase完了直後 | CRCがあれば旧値も戻るか |
| 非active bankのerase完了直後 | どちらのbankを読むか。旧active側を書き換えてよいか |
| 新しいbodyの一部を書いた後 | magicだけを見て採用してよいか |
| body後、完了印をまだ書いていない | 完了印なし／ありの形式で、読める版はどう変わるか |
| 最大世代まで使った後 | 0へ戻すと、どちらを新しいと判定するか |
| 有効な同世代のbankが2つある | 自動で片方を選ぶ根拠があるか |
| scannerが破損を報告した後 | 明示的な置換と、旧値の復旧は同じか |

今回の結果では上書きに旧値消失の区間があり、2 bankでは指定した有限の中断集合で旧値か新値を読めた。
CRCの一般的な完全検出や、実電断の影響範囲を証明した結果ではない。
中断箇所の数を故障率として比べない。

## key保存の便利さと費用を分ける

今回のkey候補はuint16の識別子とuint32の値を、最大2件のsnapshotとして保存する。
単なるuint32を2つ並べた8 Bと、識別子を含む12 Bの違いを計算する。
1件変更する操作が、今回の方式ではbank全体の消去・snapshotの書直しになる点にも注目する。
key APIがあるだけで、小更新に適した耐久性や整理方式が備わるわけではない。

次の変更では、keyを3件にする、値を可変長にする、変更を追記する場合を考える。
必要な上限、metadata、作業RAM、満杯時の戻り値、整理中に旧値を残す場所を挙げてから試作する。
今回のPython模型のlistやdictのmemory量を、MCUのRAM見積りに使わない。

## C++のRAMと呼出し内の仕事量を比べる

[C++試作の結果](store-result.ja.md)で、V003の2 B programと64 B program、X035の256 B programを比較する。
作業buffer、設定のsnapshot、管理情報、入口の変数、stackを分けてRAMを計算する。
bufferが小さくなっただけで、予約Flashや更新回数の条件まで同じになるか点検する。

試作はbank全体をRAMへ載せないが、受理時には全bankを同期走査する。
4 KiB予約の消去済み媒体でbeginは4,096回、putは8,192回のbyte readを行った。
「1媒体操作ずつstepする」と「受理・走査も短く分割される」を分けて説明する。
次は1回の走査byte数を制限した場合の追加状態と、走査中に更新を許す条件を予測する。
hostの読出し回数を、MCUのcycleや実時間にそのまま換算しない。

## byte予算と領域の所有を使う

[予算付き読出しの試作](scan-result.ja.md)は、4 KiBの空領域を32 byteずつ128回に分けて走査した。
beginが成功しても値がすぐ読めるとは限らず、明示pollで完了してからpeekする。
予算0、大きすぎる予算、途中でpeekした場合の戻り値と、出力引数の状態を予測する。

結果を読出し直さず使うため、この候補はendまで領域を所有する。
「読出しが終わったから別のRAW書込みを始めてよい」と判断すると、cacheの前提がどう変わるか考える。
所有を解放して別のownerが更新した後は、古い結果を返さず、再取得して走査し直す。
同じ台帳を使わない処理やISR／別coreからの操作まで、安全になったとは解釈しない。

同期読出しの一時stackと、分割読出しが持ち続ける状態・共有台帳のRAMを分けて比較する。
長期所有と、操作のたびに取得・解放する方法では、他の利用者の待ち方も変わる。
どの方式を使うかは、容量と進行回数を比べ、人が変更・説明できることを確認してから判断する。
