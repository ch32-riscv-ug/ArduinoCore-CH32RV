# 小さい上流実装と、保持を追加したK0を比較する

2026-10-21。[K0上流の再現と契約差](k0-upstream-result.ja.md)に対応する教材案。
人による予測・説明・変更の評価は未実施。APIや保持方式の採用を決めるものではない。

## Sourceから予測する

上流は10 Bのlive register配列、固定K0は公開snapshot8 Bと設定frame8 Bを分けている。
次を予測し、対応するsourceの処理と固定K0の契約を別々に示す。

- masterが11 byte目をreadした場合、上流とK0で何が返るか。
- 設定の途中でSTOPした場合、既存byteの保持・新byteの反映・不正通知はどこにあるか。
- 通常処理が止まっている間に設定を2回送ると、どの情報が残り、何が失われ得るか。
- read中の値を一定にしたい場合、誰が何byteをいつまで保持する必要があるか。
- mainのBUSY確認と、その後のIRQ禁止区間について、どの順序の競合を実機で確認すべきか。
- 上流のencoder pin pollと、K0の論理差分入力で、検証している事象はどう違うか。

ここでの回答は上流sourceの観察とK0のhost契約の対比であり、実IRQ／wireの証明ではない。
実機で安全かどうかを断定するために、どのevent順やpeer観測が不足するかも記録する。

## 費用を説明する

再現結果の.bssは32 Bで、選択した静的objectのsymbol合計は25 Bだった。
差分にある整列と、ここへ含まれないstack・IRQ context・外部masterの状態を説明する。
既存R/A/B/Cの表と比べる際は、実I2C・startupの有無、位置の幅、snapshot、設定保持、validation、statusを揃える。

仮に未反映設定を2件へ増やすなら、次を先に書き出す。

1. 受信staging、完成設定、適用中設定を誰が保持するか。
2. 満杯が判明した時点で、wire上のどの受理を拒否したいか。
3. 前の設定を適用した後、masterが何を根拠に再送するか。
4. 書込みが途中で失敗した場合、どこまでを返却・再利用できるか。

実装の小ささと、未提供の保証を分けて説明する。
K0の比較契約や未確定のhardware受理条件を、この課題の都合で変更しない。
