# 呼出し頻度・転送完了・新しい測定値を区別する

2026-10-21。[X0 device入力の照合と模型](x0-device-result.ja.md)に対応する教材案。
実機性能や教育効果は未評価で、bus速度・averaging・配信方式を決める課題ではない。

## 予測して再現する

結果文書のコマンドで資料を検証し、計算模型を再現する。
次を予測してからJSON／CSVと照合する。

1. payload32 Bにcontrolとaddressを加えると、storageとwireにそれぞれ何byte必要か。
2. frame先頭だけwindowを設定する場合と各chunkで設定する場合で、どの状態を保持し、どの転送が増えるか。
3. 128×64の全画面転送を100 kHzで毎秒10回要求すると、clock計数だけでどれだけ占有するか。含めていない時間は何か。
4. 同じrenderer出力をhorizontal／verticalへ渡すと、RAMの配置とwire列のhashはどう変わるか。
5. 136.2 ms周期の完了tagを100 msごとに読む模型で、10回のreadが10個の新しいtagにならない理由は何か。
6. INAの通信が成功しても、旧conversion・OVF・calibration喪失を区別すべき理由は何か。

## 実機検証の設計

IRQ／通常処理のどちらが次byteを進めるかを、sourceと外部の線から説明する。
通常処理を止める位置を選び、停止中のSCL／SDA、相手のtimeout、再開後のprefix・回収結果を記録する案を作る。
28 msという資料値を、そのまま全taskの時間保証へ変換しない。

計測では、要求数・通信成功数・新conversion数・用途反映数を別々に記録する。
CNVRのlevelを読めただけで、新しいcycleを識別できたと判定しない。clear条件の未確認部分も残す。
panelのRAM模型と、実pixel・orientation・電源初期化の成功を区別する。

## 評価記録

予測、模型の結果、含めていない費用、実機で必要な観測、追加状態を記録する。
速いbusや短いaveragingを選ぶ前に、同じ情報・精度・失敗処理で比較できるかを説明する。
利用者がこれらを説明・変更できるかは、人によるレビューを取得して評価する。
