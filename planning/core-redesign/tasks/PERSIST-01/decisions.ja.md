# PERSIST-01 決めてほしいこと(判断の材料)

2026-10-28。[plan.ja.md](plan.ja.md) の出口(5 章の 7)。測定は [measurements.ja.md](measurements.ja.md)、他の環境は [survey.md](survey.md)、PC 上の試作は [EXP-04](../EXP-04/)。

決まっていること: raw の関数は公開する。書き込み直しで中身を残す方向。

## 前提: CH32 で何を保存するか

保存するのは、人の操作のとき・工場・初回にだけ書く、小さい値とする。

| 用途 | このプロジェクトの例 | 大きさ | 書く頻度 |
|---|---|---|---|
| 設定 | X0(X035 の PD アダプタ)の PPS の目標値 8 B、Network のホスト名 33 B・MAC 6 B・固定 IP | 数 B〜数百 B | 人が設定を変えたとき |
| 校正値 | `touchRead()` の基準値、LSI の測定値 | 数 B〜数十 B | 工場か初回だけ |

- 調査(survey.md)の「数え上げ」「最後の状態を分ごとに保存」は、ESPHome・Tasmota など ESP の家電ファームの使い方。CH32 の利用者がそうするという根拠は無いので、前提にしない。
- 頻繁に変わる値は、フラッシュに置かない。RAM・`.noinit`・BKP に置き、必要なら休止や電源を切る前だけ書く、と案内する(BKP と `.noinit` はもう使っている)。
- 記録(履歴)はこの保存の対象外(ファイルシステムか SD)。

この前提だと、書き換えの寿命は判断の決め手にならない。2 面の入れ替えで、10K 回の系列でも 1 日 10 回で約 5.5 年、1 日 100 回でも約 200 日。足りない場合の手当ては Q3 に書いた(面の数を増やす)。

## 0. 判断に使う数字

### 系列ごとの性質

| 系列 | 小さい型番のフラッシュ / RAM | 高速の消去の単位 | 書き換えの寿命(最小) | 消去後 | 消去・書き込みで CPU |
|---|---|---|---|---|---|
| V003 | 16 KB / 2 KB | 64 B | 10K | 0xFF | 止まる |
| V002、V006F4 | 16 KB / 4 KB | 256 B | 100K〜300K | 0xFF | 止まる |
| V004、V005 | 32 KB / 6 KB | 256 B | 100K〜300K | 0xFF | 止まる(V006 で測った) |
| V006、V007、M007 | 62 KB / 8 KB | 256 B | 100K〜300K | 0xFF | 止まる |
| V103 | 32 KB / 10 KB | 128 B | 10K | 0xFF | 止まる |
| V203 | 32 KB / 10 KB | 256 B | 10K | 0xE339 | 止まらない |
| X035、L103 | 62〜64 KB / 20 KB | 256 B | 300K | 0xFF | 止まる |
| V205 | — | 256 B | 300K | 0xFF | 止まる |
| V30x | — | 256 B | 10K | 0xE339 | 止まらない |
| X315 | — | 4 KB(標準のみ) | 50K | 0xE339 | はっきりしない |
| H417 | — | 4 / 8 KB(標準のみ) | 50K | 0xE339 | 止まらない(RAM で実行) |

- 小さいのは V003 だけではない。V002、V006F4 も 16 KB。V003 の RAM は 2 KB しかない。
- 消去後が 0xE339 の系列でも、消去したページに 1 回だけ書くなら問題ない(M3、M12)。どの形式も 12 ファミリーで同じに使える。

### 1 回の保存で止まる時間(実測の値から計算)

| 系列 | 64 B の中身(1 単位を消して書く) | 256 B の中身 | 1 KB の中身 |
|---|---|---|---|
| V003 | 6.0 ms | 約 24 ms | 約 96 ms |
| X035 | 4.6 ms | 4.6 ms | 約 18 ms |
| V006 | 4.7 ms | 4.7 ms | 約 19 ms |
| L103 | 8.8 ms | 8.8 ms | 約 35 ms |
| V205 | 8.6 ms | 8.6 ms | 約 35 ms |
| V203 | 10.7 ms(止まらない) | 10.7 ms | 約 15 ms |
| V307 | 18.5 ms(止まらない) | 18.5 ms | 約 23 ms |
| X315 | 4.0 ms | 4.0 ms | 約 7 ms |

- 見出しの 16 B を含めると単位を 1 つはみ出す大きさ(V003 の 64 B ちょうど、ほかの 256 B ちょうど)は、1 単位多くなる。
- CPU が止まる系列では、止まった間に UART に届いたバイトはほぼ全部落ちる(M2)。115200 bps では 1 ms に約 11.5 B。V003 で 64 B を保存すると約 70 B、X035 で約 50 B。止まらないはずの V203、V307 でも、消去の時間の 3〜5 割の分が落ちた。
- 止まる系列では、止まった間 `millis()` が進まない(M11、Q6)。
- 人の操作のときに書くなら、この時間は問題になりにくい。通信の最中に保存するスケッチだけが気にすればよい(文書に書く)。

### コードと RAM(V003、LTO あり、EXP-04)

| 形 | コード | RAM |
|---|---|---|
| raw | 約 0.75 KB | ほぼ 0 |
| 1 面の上書き(固定の 8 B) | 約 1.6 KB | 作業用 64 B |
| 2 面の入れ替え(固定の 8 B) | 約 1.8 KB | 作業用 64 B |
| EEPROM の API | 上の形 + API の分(未測定) | `begin(size)` の size バイト(RAM に写しを持つ) |

- EXP-04 の数字は試験の入口と仮の媒体を含み、本物のフラッシュの処理を含まない。実装したら空のスケッチとの差を測り直す。

## Q1. 電源断・WDT のリセットで、何を約束するか

### 起きること(実測)

- 電源断(M5): 消去・書き込みの途中で切ると、途中の状態が 30 回中 0〜3 回残った(9 系列)。中身は「全部 0」「一部だけ書けた」「読むたびに値が変わる語」。
- WDT のリセット(M4): CPU が止まる系列と X315 では、240 回中 5〜30 回、途中の状態が残った。V203、V307 では 0 回。
- 1 面を上書きする形では、消去が終わってから書き終わるまでの間に切れると、**前の中身も新しい中身も無くなる**。V003 の 64 B なら約 6 ms の窓。

人が設定を変えるのは、電源を入れ直す直前のことが多い(設定を変えて、抜いて、付け直す)。保存中に電源が切れる場面は、頻度が低くても現実にある。

### 選択肢

| 選択肢 | 利用者から見えること | 費用 | 他の環境 |
|---|---|---|---|
| A. 約束しない(1 面の上書き) | 保存の途中で電源が切れると、全部の設定が消えることがある | 確保は 1 単位。コードは約 0.2 KB 小さい | ESP8266、RP2040、STM32duino の EEPROM |
| B. 前の中身か新しい中身のどちらかが残る(2 面の入れ替え) | 途中で切れても、最後に保存し終えた中身が残る。壊れた中身は見せない | 確保は 2 単位(V003 で 128 B から)。CRC と世代を持つ | Arduino の EEPROM の真似には無い。ESP32 の NVS、mbed、Zephyr は守る |

- B でも約束できないこと: 寿命を超えた書き換え、電圧の低い状態での書き込み、CRC が偶然合う場合。
- WDT の時間が保存の時間より短いと、保存は毎回途中で止まる。保存の時間の上限を系列ごとに文書に書き、WDT が有効なら消去の前に餌をやる(raw の層)。

### 推奨: B

- 途中の状態が実際に残ることを測定で確かめた。費用は 1 単位と約 0.2 KB で、V003 でも払える。

## Q2. 利用者に見せる API

| 選択肢 | 書き方の例 | RAM | 良いところ | 困るところ |
|---|---|---|---|---|
| A. Arduino の EEPROM の API + `begin(size)`、`commit()` | `EEPROM.begin(64); EEPROM.put(0, cfg); EEPROM.commit();` | size バイトの写し | Arduino の定番。EEPROM を使う既存のライブラリ・例が、`begin` と `commit` を足せば動く(ESP8266、RP2040 と同じ形) | AVR と違い、`commit()` を忘れると保存されない。番地は利用者が割り振る |
| B. 構造体を 1 つ保存する型 | `Saved<Config> cfg; cfg.load(); cfg.save();` | 構造体の大きさ | 設定を構造体にまとめる、小さいマイコンでよくある書き方そのもの。番地が要らない | 定番の API ではない。構造体を変えたときの扱いを利用者が考える |
| C. キーと値(ESP32 の Preferences の形) | `prefs.putUInt("pps", mv);` | 記録 1 件分 | 名前で持つ | ESP32 の使い方。キーの表や名前の分、コードと領域が大きい。CH32 の小さい値の保存には重い |

### 推奨: A。B は A の上の例として示す

- A は Arduino の利用者がいちばん知っている形。V003 でも、中身を 64〜256 B に抑えれば RAM に収まる。
- `commit()` を忘れる落とし穴は、例と文書で示す。`end()` で commit する。
- C は今は作らない(前提の用途に要らない)。

## Q3. 下の形式

Q1 が B なら、2 面の入れ替え。

- 同じ大きさの面を 2 つ置き、交互に書く。面の頭に、magic、世代、長さ、CRC を置く。
- 起動時は、CRC が合う面のうち、世代が大きいほうを読む。読むたびに値が変わる語(M5)に備えて、CRC は 2 回計算する。
- 中身が変わっていなければ書かない。同じ値を何度 `commit()` しても減らない。
- EXP-04 の模型で、中断 7,442 条件で旧値か新値になった。実機の電源断は、実装してから M5 の手順で確かめる。

### 寿命が足りない用途への手当て(選択肢)

| 選択肢 | 中身 | 費用 |
|---|---|---|
| a. 2 面のまま | 10K 回の系列で 20K 回の保存。1 日 10 回で約 5.5 年 | なし |
| b. 面の数を増やせるようにする(輪番) | N 面を順に使う。寿命は N/2 倍。V003 で 64 B の面を 8 つ(512 B)なら 80K 回 | 2 面とほぼ同じコード。確保が増える |

### 推奨: a で作り、b は大きさの宣言で面の数を増やせる作りにしておく

- 前提の用途では a で足りる。b は形式を変えずに足せる(面を選ぶ規則が「世代のいちばん大きい面」のまま)。

## Q4. 領域の大きさを、どこで決めるか

### 前提

- 領域はフラッシュの末尾に置く。スケッチの大きさが変わっても動かない。
- リンカーは、領域の大きさを**ビルドのとき**に知る必要がある。`EEPROM.begin(size)` の size は**実行時**の値なので、確保の大きさはそれで決められない。
- 確保した分は、Arduino が表示するスケッチの使用量に入らない。スケッチが末尾まで伸びると、リンクで止まる(flash-raw)。
- 型番のメニューを変えると、末尾が動いて前の中身を見つけられない(例: V006 の ANY は 16 KB、K8 は 62 KB)。

### 選択肢

| 選択肢 | 中身 | 使わないとき | 他の環境 |
|---|---|---|---|
| A. 系列ごとの既定の大きさ。EEPROM を使ったときだけ確保。スケッチが 1 行で変えられる | 例: V003 は 2 面 × 128 B、そのほかは 2 面 × 256 B か 1 KB。変えるときは `.ino` に `CH32RV_EEPROM_SIZE(512);` のような宣言を書く(リンカーの weak な記号で、宣言があればそちらを使う) | 0 B | ESP8266、RP2040 は固定の 4 KB |
| B. 系列ごとに固定で、常に確保 | EEPROM を使わないスケッチでも末尾を空ける | V003 で 256 B を常に失う | RP2040 は 4 KB を常に確保 |
| C. ボードメニューで選ぶ | `EEPROM Size: None / 128 B / 512 B / 2 KB` | None なら 0 B | EEPROM の大きさをメニューで選ばせるコアは、調べた中に無い |

- `begin(size)` に、確保より大きい値を渡したら失敗にする。
- A と C では、EEPROM を使うスケッチと使わないスケッチで末尾の扱いが変わる。Q5 で「宣言した範囲だけ残す」を選ぶと、使わないスケッチを書いた時点で中身が消える。

### 推奨: A

- 使わなければ 0 B(このプロジェクトの方針)。ふつうの利用者は何も触らない。
- 型番を変えると中身を見つけられないことは、文書に書く。

## Q5. 書き込み直しで残す手段と、全部消す手段

### 今の動き(M6)

| 経路 | 渡すファイル | 今の既定(`--erase auto`) |
|---|---|---|
| LinkE の V003、X035、L103、V20x、V30x(WCH のスタブ) | ELF | チップ全体を消す → **消える** |
| LinkE の V205、X315、V006(ch32rv のローダー)、OEP の全部 | ELF | イメージのページだけ消す → 残る |
| H417 の DFU | bin | 残る |
| V003 の HID のブートローダー | bin | 未測定 |
| 工場の ISP | ELF | 未測定 |

- 同じ LinkE でも、系列によって残ったり消えたりする。今のままでは利用者に説明できない。
- `--erase sector` にすれば全部で残るが、スタブの経路では書き込みが 3〜7 倍遅い(V307 の 97 KB で 4.2 秒 → 30 秒、V003 で 2.5 秒 → 12 秒)。
- 末尾を LinkE で読む時間(2026-10-28、接続の約 0.15 秒を含む): 1 KB と 4 KB で約 0.2 秒、16 KB で約 0.4 秒(V003、V203、V307)。

### 残す手段(どれも ch32rv の変更)

| 選択肢 | 中身 | 書き込みの時間 | EEPROM を使わないスケッチを書いたとき | わかっていないこと |
|---|---|---|---|---|
| 1. ELF の領域を退避して書き戻す | ch32rv が新しい ELF の領域の範囲を読み、全体を消す前にその範囲を読んでおき、書き込みのあとで書き戻す | 今 + 約 0.1〜0.3 秒(読みは実測、書き戻しは未測定) | スタブの経路では**消える**。ローダーの経路では残る | 書き戻しの途中で失敗したときの扱い |
| 2. スタブの経路でも、イメージのページだけを速く消す | ローダーの経路と同じ消し方に、全部の経路をそろえる | 未測定。ローダーの経路(V205)は 1 KB を 0.31 秒で消している | 末尾は**常に残る** | ch32rv がスタブの系列でも速く消せるか。ch32rv のセッションに聞く |

- 調べたほかのコアは、どれも「書いたところだけ消す」が既定で、全体を消すのは名前の付いた選択。選択肢 2 はこれと同じ動き。
- 選択肢 1 では、EEPROM を使わない試しのスケッチを一度書いて戻すと、LinkE の V003 などでは中身が消え、OEP では残る。違いが利用者に見えにくい。

### 全部消す手段

| 選択肢 | 中身 |
|---|---|
| a. ボードメニュー `Erase Flash: Sketch Only (default) / All Flash` | 表示は英語 |
| b. ch32rv のコマンドを文書で案内 | メニューは増えない |
| c. スケッチから消す(EEPROM の中身を初期化する関数) | 工場出荷に戻す用途 |

### 推奨: 残す手段は 2。全部消す手段は a と c

- 経路にもスケッチにもよらず「書き込み直しで残る」と一文で説明できる。
- 2 が速くできるかは ch32rv しだい。まず ch32rv のセッションに聞き、できないか遅いなら 1 にする。
- HID と ISP の経路は、測ってから文書に書く。

## Q6. 止まった時間を `millis()` に足すのを、コア全体で直すか

- コアの SysTick の割り込みは、1 ms ごとにカウンターを 0 に戻す。割り込みが入らない間に何 ms たっても、`millis()` は 1 しか進まない(M11)。フラッシュに限らず、割り込みを長く止めた処理のあとでも同じ。

| 選択肢 | 中身 | 影響 |
|---|---|---|
| A. raw の層だけで足す | 消去の前後で SysTick の数を読み、足りない ms を足す | 保存だけが正しくなる |
| B. SysTick の割り込みで直す | 0 に戻す前に、何 ms 分進んでいたかを数えて足す | 割り込みを止めた処理の全部で直る。全系列の時間の基本に触るので、試験をやり直す |

### 推奨: A を先に。B は別の課題として起こす

## raw の層(公開は決定済み)に入れること

- 書き込みのたびに、終わりで CTLR を 0 に戻し、STATR の WRPRTERR を消す(M10。残すと、あとでデバッガのオプションバイトの操作が壊れる)。
- WR_BSY を待つループは、WRPRTERR を見て止まるか、時間で打ち切る(M10)。
- WDT が有効なら、消去の前に餌をやる(M4、M11)。
- 止まった時間を `millis()` に足す(Q6 の A)。
- 書いたあとに読み直して比べる。
- 文書に、系列ごとの止まる時間と、その間に UART で落ちうるバイト数を書く(M2)。
- 保存の領域を書き込み保護しないこと、読み出し保護の状態での動きは確かめられていないことを書く(M10)。

## 測ったが、この前提では判断に使わなくなったもの

- ログ型(ZMS 型)が 0xE339 の系列でも成り立つこと(M12)。頻繁に書く用途が出てきたら、raw の上に作れる。
- 起動時の走査の時間(M8)。2 面なら頭を 2 つ読むだけ。

## 答えが出たあとにすること

1. ch32rv のセッションに、Q5 の選択肢 2 ができるかを聞く。
2. raw の層と 2 面の EEPROM を実装し、大きさ(V003、X035、V307)と電源断(M5 の手順で各 30 回)を測る。
3. まだ測っていないこと: 保存の間の USB と DMA(相手のスケッチが要る)、V103、HID・ISP の経路、読み出し保護の状態での動き(LinkE を外せる台が要る)。
