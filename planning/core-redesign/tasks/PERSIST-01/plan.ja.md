2026-10-28 に始めた。**仕様は決めない。** 用途の調査と実機の測定を先にとことんやり、その結果から全体の形・領域の大きさ・書き込み直しの扱いを練り直す(利用者の指示)。

決まっていること(2026-10-28、利用者):
- フラッシュの raw の関数は、利用者に公開する。
- スケッチを書き込み直したときに、保存した中身を残す方向。ただし、その手段(ch32rv の既定の消去を変えるか、メニューか)は全体の計画しだいで、今は決めない。ch32rv への依頼は保留にした。

## 0. やり直し(2026-10-28、利用者の指摘)

**指摘:** 全体の計画からアンバランス。摩耗だけを気にして調査し、コストを計算していない。小さいマイコンで他のコアがどうしているかを調べ、仮説を立ててやり直す。数百 B はかなり大きい。そこを詰めないと、仕様の方向性は決められない。

これを受けて、次のように扱う。

- 1〜4.1 章と [decisions.ja.md](decisions.ja.md) は、ESP32 の使い方と摩耗に寄った調査の上に立っている。**取り下げる**。測定（M1〜M13）の数字は使う。
- 物差しの中心を「バイト数」にする。V003（16 KB / 2 KB）で、機能ごとにコード・RAM・確保の増分を並べる。
- 材料:
  - 小さいマイコンのコアのソースの調査: [survey-small.md](survey-small.md)。
  - 同じスケッチでの実測: [measurements.ja.md](measurements.ja.md) の M14。

### 0.3 次に測ること

1. H4 の (a)(b)(c) を V003 で作り、M14 と同じスケッチで測る。(c) は、V003 の 2 バイト書き込みと、ページのバッファの一部だけを書く書き込み(M12)の両方で。→ 済み(M15、0.4)。V003 には 2 バイト書き込みがないので、(c) はバッファの一部だけを書く方式で作った。
2. H3: 最小の raw と 2 面を、X035(バッファの方式、256 B)と V203(直接書く方式、0xE339)で測る。
3. 1 と 2 の表を作ってから、方向性(API、形式、写しの有無、電源断の約束)を相談する。

### 0.4 最小から積み上げたコスト(M15、V003)

**指摘(2026-10-28):** 書き込みの時間の補正なども抜いた、コストが最小の形から積み上げる。そこから、利点とコストを見て、どこまで入れるかを決める。使う人が、ある程度コストを計算して選べるようにしたい。

| 層 | 足すもの | 増える B | 利点(無いとどうなるか) |
|---|---|---|---|
| 床 | 1 ページを消して書く | +208(関数は 158) | — |
| raw の安全 | 割り込みを止める | +12 | V003 では見つかっていない。CPU がもともと止まり、床のまま 150 回書けた。CPU が止まらない V203 などでは要確認 |
| | 前後の状態を消す | +12 | 失敗したときだけ効く。残ったエラーで ch32rv が次の書き込みを読み違える(M10) |
| | 待ちの上限と結果 | +28 | 保護などで失敗しても止まらず、false が返る。無いと永久に止まる。普通の使い方では保護は掛からない |
| | `millis()` の補正(固定) | +24 | 1 回書くごとの約 4 ms の遅れを戻す。人の操作で書くなら、気にならない |
| | `millis()` の補正(実測) | +68 | 固定と同じ。クロックや系列が変わっても合う |
| | 書いた後の読み直し | +32 | 書けなかったこと(寿命の末期など)に気づける |
| 形 | (a) 構造体の load / save | +32 | 1 回で全部を書く。読むのはほぼ 0 |
| | (a) に、書いたことがあるかの印 | +24 | 初めての起動を見分けて、既定値を入れられる |
| | (a) に、変わらなければ書かない | +40 | 同じ値で書き直さない(時間と寿命) |
| | (b) AVR の API(1 ページ、写しなし) | +104 | 既存のスケッチがそのまま動く。変わらなければ書かない、を含む。容量は 64 B |
| | 2 面(世代と CRC) | +260 | 書いている途中で電源が切れても、前の値が残る。書いたことがあるかも分かる |
| | (c) 追記ログ(Teensy 型) | +376 | 書き込みが約 2 倍速く(消さない)、消す回数は約 1/32。容量は 16 B |

「層」の増分は、床からの差です(raw の安全の項目)。「形」の増分は、床の raw の上に載せたときの差です。組み合わせると、ほぼ足し算になります。

比べると、次のとおりです。

| コア | 書くまで使ったときの増分 |
|---|---|
| AVR(本物の EEPROM) | +64 B |
| STM32duino(フラッシュで模倣、16 KB 品) | +780 B と、RAM 1〜2 KB |
| openwch の V003 | +1.1 KB |
| (b) AVR の API(床の上) | +260 B |
| 2 面(床の上) | +468 B |
| 床の raw だけ | +208 B |

仮説の確かめ:

- **H1(写しなし):** 確かめた。写しなしで AVR の API を出せた。RAM は 0 で、+260 B。写しを持つ STM32duino の 1/3 の大きさ。
- **H3(下限は raw):** 確かめた。ただし床は 324 B ではなく、158 B だった。前の 324 B は、`|=` での書き方と、割り込みの停止を含んでいた。
- **H4(API が費用を決める):** 確かめた。
  - (b) +104 は、Teensy 型の (c) +376 より小さい。
  - 写しなしの AVR の API に、追記ログは要らない。
  - (c) の利点は、速さと寿命だけになる。V003 の使い方(人の操作で書く)では、その利点は小さい。
- **H2(電源断の費用):** 床の上で +260 B。前の見積もり(+232)は、別名の誤りで小さく出ていた。

選べるようにする仕組み(まだ決めない、相談する):

| 案 | 選び方 | 良い点 | 困る点 |
|---|---|---|---|
| A | 層を別の関数・クラスにする(raw、load / save、EEPROM、2 面)。使ったものだけがリンクされる | 表を見て選べる。使わなければ 0 B | 安全の項目は、層の中に固定になる |
| B | 安全の項目を、ボードのメニューで選ぶ | IDE の上で見える | メニューが増える。ライブラリの作者が前提にできない |
| C | スケッチで `#define` してから include する(ヘッダーだけの実装) | 細かく選べる | Arduino では、ほかの .cpp に届かない。気づきにくい |

### 0.5 位置づけ(2026-10-28、利用者が決めた)

**推奨は外部に保存すること。** SPI でつなぐ SD や、I2C でつなぐ EEPROM を使う。

**内蔵のフラッシュに書くこともできるが、上級者向けの選択肢とする。** 次の制約があるからである。

| 制約 | 中身 | 根拠 |
|---|---|---|
| 寿命 | 1 万回の系列がある。60 秒ごとに書くと約 7 日でだめになる | survey-usage の V003 の作例、persistence-spec |
| ファームの書き込み直し | 経路によって消えたり残ったりする。残った場合は、別のファームが古いデータを読む | M6、M16 |
| 消す単位 | ページを丸ごと消す(V003 で 64 B、X035 で 256 B)。1 バイトずつは書き換えられない | M1、flash-raw |
| 書く単位 | 一度書いた語に、消さずに重ねて書けない系列がある(0xE339 の系列)。消したあとの値も、系列で違う | M3、M12 |
| 書いている間 | V003 では約 6 ms、CPU と割り込みが止まる。UART の受信が落ち、`millis()` が遅れる | M2、M15 |
| 電源断 | 1 ページの形では、書いている途中で切れると値が壊れる | M5、flash-raw |

この位置づけから、出すものを次のとおりにする。

| 出すもの | 中身 | 費用(V003) |
|---|---|---|
| コアの raw | 領域の確保(リンカの区画、M13)と、1 ページを消して書く関数。安全は最低限で、待ちの上限と状態を消す処理だけを入れる | 約 +250 B(V003 +248、X035 +264、V203 +244、M17)。RAM 0 |
| サンプル 1 | 1 ページの load / save と、版の確認 | M16 |
| サンプル 2 | 2 面(電源断に強い形) | M15、M16 |
| `EEPROM.h` | 出さない | — |

- 文書の頭に、推奨は外部の SD や EEPROM であることと、上の制約の表を置く。
- `millis()` の補正と読み直しは raw に入れない。文書に費用を示し、必要な人がスケッチで足す。
- ESP32 でも `EEPROM.h` は 2019 年 4 月から非推奨になっている(arduino-esp32 の `libraries/EEPROM/README.md`: "EEPROM is deprecated. For new applications on ESP32, use Preferences.")。

残っていること:

1. 外部に保存する推奨の経路は、このタスクでは扱わない。別のタスクにある。
   - SD とファイルシステム（FAT に何を使うか）: [docs/filesystem.ja.md](../../../../docs/filesystem.ja.md)（TODO.ja.md の「USB の外で要るスタック」、2026-10-21 に着手）。永続化と同じくらいの検証が要る。
   - I2C の EEPROM: TODO.ja.md の例の表の `I2CEeprom`（ページ境界と、書き込みの完了を待つこと）。
   - このタスクの文書からは、そちらへ案内するだけにする。
2. raw の最低限の安全の形を、V203(CPU が止まらない、0xE339)と X035(256 B のページ)でも測る。→ 済み(M17)。
   - 床は 3 系列とも約 200 B。最低限の安全(状態を消す、待ちの上限)は +48 B。
   - 割り込みを止める項目は入れない。利点が見つからず、`millis()` を遅らせるだけだった。
   - `millis()` の補正は入れない。V203 では要らない。SysTick で測る形は、X035 で壊れた。
3. 書き込み直しで消えるかは、経路ごとの表にしない。ツールの版で変わりうるため。文書には「書き込み直しで消えることがある(経路とツールの版による)」とだけ書く。

API の案: [api.ja.md](api.ja.md)(M18)。2026-10-28 に、全系列で同じ関数を出す形(M19)でコアに入れた。利用者向けは [docs/flash-store.ja.md](../../../../docs/flash-store.ja.md)、例は `libraries/CH32RV/examples/FlashSettings`、`FlashSettingsTwoBanks`。

済んだこと: M030、V407、X315 で書く間に CPU が止まるか(M20)。H417 の DFU(M19)。2 面の形の電源断(M21)。経路ごとに保存が残るかは、方針により調べない(0.5 の 3)。

## 1. 用途から要求を出す

保存したいものを並べ、それぞれの大きさ・書く頻度・電源断で許せること・書き込み直しで残したいかを書く。要求は「どの候補が満たすか」を測る物差しにする。

| 用途 | 一般の例(survey.md 2 章) | このプロジェクトの例 | 大きさ | 書く頻度 | 電源断で許せること | 書き込み直しで |
|---|---|---|---|---|---|---|
| 設定 | Wi-Fi の設定(約 80 B)、grbl の設定(約 1 KB)、表示の明るさ | X0(X035 の PD アダプタ)の PPS の目標値 8 B、Network のホスト名(33 B)・MAC(6 B)・固定 IP | 数 B〜1 KB | 人の操作のたび(まれ) | 旧値か新値 | 残したい |
| 校正値 | BNO055 の校正 26 B、ADC のずれ | `touchRead()` の基準値、LSI の測定値(今は RTC の BKP に置く) | 数 B〜数十 B | 工場か初回だけ | 旧値か新値。消えると困る | 残したい |
| 識別と秘密 | 機器名、鍵、証明書 | — | 数十 B〜数 KB | まれ | 旧値か新値 | 残したい(鍵は消したい場合も) |
| 最後の状態 | 最後の出力(リレー、明るさ)、ESPHome の restore | K0(V003 の I2C ノブ)の位置 8 B | 数 B〜数十 B | 変わるたび(間隔を絞る前提: 秒〜分) | 少し前の値に戻ってよい | 残したい |
| 数え上げ | 起動回数、電力量、使用時間 | — | 4〜8 B | 頻繁(秒〜分ごと) | 少し戻ってよい | 残したい |
| 記録 | センサの履歴、イベントのログ | — | KB〜MB | 一定間隔 | 最後の数件は失ってよい | どちらも |
| 休止をまたぐ状態 | 休止(スタンバイ)の前の状態 | `deepSleep()` の起床の理由(`.noinit`)、RTC の時刻(BKP) | 数 B〜数十 B | 休止のたび | 失ってよい場合が多い | 不要 |

- 「最後の状態」と「数え上げ」は、書く回数で寿命が決まる。1 ページを毎回消して書くと、10K 回の系列(V003、V103、V20x、V30x)では、1 分に 1 回で約 1 週間しかもたない。8 B の記録を 256 B の高速ページに書き足していけば(消去後 0xFF の系列)、1 回の消去で 32 件になり、2 KB を回せば約 5 年(10K × 256 件 ÷ 1 分に 1 件)。0xE339 の系列で同じことができるかは M12 で確かめる。
- 「休止をまたぐ状態」は、もうフラッシュ以外で済ませている(`.noinit`、BKP)。永続化の対象からは外し、置き場所の案内だけを書く。
- 「記録」「証明書」は、設定の保存と分ける(ファイルシステムか SD)。
- 校正値で、コアが持つもの(LSI)は BKP に置いている。BKP は電源を切ると消えるので、フラッシュに移すかは、保存の形が決まってから考える。

## 2. 他の環境の調査(済み: [survey.md](survey.md)、2026-10-28)

要点(事実は survey.md の出典つき。ここでは判断に効くものだけ):

| 環境 | 形 | 確保の最小 | 電源断 | 書き込み直しで | 大きさの決め方 |
|---|---|---|---|---|---|
| ESP32 Preferences / NVS | キーと値、4 KB ページのログ(状態のビットを同じ語に書き足す) | 12 KB(Arduino の既定 20 KB) | 書いている値だけ失う | 残る(esptool は書く範囲だけ消す。全部消すメニューあり) | パーティション表 |
| ESP32 EEPROM | NVS の上の 1 つの塊 + RAM の写し | NVS と同じ | NVS と同じ | 残る | `begin(size)` |
| ESP8266 / RP2040 EEPROM | 4 KB を 1 面、RAM の写し、`commit()` で消してから書く | 4 KB | **守らない**(消した直後に切れると全部失う) | 残る(RP2040 は picotool load。ESP8266 はメニューで選ぶ) | リンカーの記号で固定 |
| STM32duino EEPROM | 最後のページ。書くたびに消して書く(バッファつき API は別) | 1 ページ | 守らない | 残る | 固定 |
| SAMD FlashStorage | スケッチのイメージの中 | — | — | **消える**(避けるべき例) | — |
| nRF52 InternalFS | LittleFS | 28 KB | 守る(ただしマウントに失敗すると黙って初期化) | 残る | 固定 |
| mbed TDBStore | 2 領域の追記ログ + 回収、RAM にキーの表 | 2 領域 | 守る | スケッチの後ろに置く例では、スケッチが伸びると動く | アプリ |
| Zephyr NVS | 追記ログ、2 セクター以上、消去後の値を 1 つの byte で比べる | 2 セクター | 守る | — | devicetree |
| Zephyr ZMS | 追記ログ。CRC と周回の数が合うものだけ有効、同じ場所は 1 周に 1 回だけ書く | 2 セクター以上 | 守る | — | devicetree |

用途の調べ(survey.md 2 章): 実際に保存されるのはほとんどが数十 B〜1 KB で、まれにしか書かない(Wi-Fi の設定 約 80 B、BNO055 の校正 26 B、grbl の設定 約 1 KB)。頻繁なのは数え上げ・最後の出力の状態・電力量で、成熟した製品は書く間隔を絞っている(ESPHome は既定で最大 1 分に 1 回、Tasmota は 1 秒ごとだが 7 個の場所を回し、変わっていなければ書かない)。AVR の EEPROM の例(10 回/秒)をそのまま 10K 回のフラッシュに移すと、約 17 分で寿命に達する。記録や証明書は、実際には SD カードやファイルシステムに置かれる。

判断に効く見立て(推測。測って確かめる):
- **書き込み直しで消さないのは、調べたどのコアでも既定**。全部消すのは、名前のついた明示的な選択(メニューかコマンド)。
- **EEPROM の大きさをメニューで選ばせるコアは無い**。ファイルシステムの大きさは、どこもメニュー。
- **Arduino の EEPROM の模倣で、電源断に耐えるものは無い**。キーと値・ファイルシステムは耐える。
- **0xE339 の系列(V20x、V30x、X315、H417)では、NVS 型(消去後 0xFF で、あとから 0 を足す)は成り立たない**。ZMS 型の規則(1 周に 1 回だけ書き、CRC と周回で見分ける)、2 つの写し + CRC なら成り立つ(M12 で、消去済みの語を別の回に書けることを確かめた)。littlefs も消去後のビットを 1 とみなすので、確かめが要る。
- CH32 の先例: openwch の V003 の EEPROM はオプションバイトの領域に 26 B。

### 1 章の表への反映

- 「設定」「校正値」「識別」は数十 B〜1 KB、まれに書く。ここが中心の要求。
- 「数え上げ」は、間隔を絞る前提でも、10K 回の系列では 1 ページを使い回すと足りない。複数の場所を回す(Tasmota、ZMS)か、BKP / RAM と組み合わせる必要がある。
- 「記録」「証明書」は設定の保存と分ける(ファイルシステムか SD)。

## 4.1 候補を物差しで並べる(2026-10-28、測定の結果から)

**前提の訂正(2026-10-28):** この節の「1 分に 1 回」の寿命の比較は、ESPHome・Tasmota など ESP の家電ファームの使い方を持ち込んだもので、CH32 の利用者の根拠は無い。CH32 では、人の操作・工場・初回にだけ書く小さい値を前提にする。この前提で選択肢と推奨を組み直したものは [decisions.ja.md](decisions.ja.md)。

系列ごとの 1 回の commit(高速ページ 1 枚の消去と書き込み)の時間は、M1・E4 による。

|---|---|---|---|
| V003 | 64 B | 約 6 ms | 止まる |
| X035 | 256 B | 約 4.5 ms | 止まる |
| V006 | 256 B | 約 4.7 ms | 止まる |

| V205 | 256 B | 約 8.6 ms | 止まる |

| V203 | 256 B | 約 10.7 ms | 止まらない |

読み取れること(推奨はまだ。相談の材料):

- **1 面の上書き** は、ほかの Arduino のコアの EEPROM と同じだが、M4・M5 で示したとおり、消去の途中の電源断や WDT のリセットで中身を全部失う。CH32 では消去が長い(V003 の標準で 50 ms)ので、この窓は広い。
- **ログ型** は、M12 で 0xE339 の系列でも成り立つと分かった。12 ファミリーで同じ形が使える。1 回の保存では消去がいらないことが多く、止まる時間が短く、摩耗も均される。「最後の状態」「数え上げ」の用途は、ログ型でしか現実的な寿命にならない。コードは 2 面より大きく、起動時の走査がある(M8: 読むだけなら軽い。CRC の範囲は形式で絞る)。
- **2 面の入れ替え** は、電源断には強いが、毎回の保存で 1 単位を消すので、摩耗と止まる時間はログ型より悪い。
- **LittleFS** は、小さい系列に入らず、0xE339 の確かめも要る。大きな系列(V30x、H417 など)の記録用途に、別に考える。
- **フラッシュ以外** は、休止をまたぐ状態用(もう使っている)。案内だけ。

形式によらない共通の論点:

- **書き込み直しで残す(M6)。** 今の ch32rv の既定では、スタブの経路(LinkE の V003、X035、L103、V20x、V30x)で消える。`--erase sector` は 3〜7 倍遅い。手段の候補は次の 3 つ(どれも ch32rv の変更で、ch32rv のセッションへの依頼になる)。
  1. ELF の保存の領域(NOLOAD のセクション)を ch32rv が読み、全体を消す前にその範囲を読んで、あとで書き戻す。速さは今の auto とほぼ同じ。
  2. スタブの経路でも、イメージが覆うページだけを速く消す。
  3. IDE のメニューで、全部消すか残すかを選ぶ。
- **raw の関数(公開は決定済み)。** M10 で、書き込み保護のページへの書き込みは WR_BSY が下がらず止まると分かった。WRPRTERR を見るか時間で打ち切る、WDT が有効なら消去の前に餌をやる、止まった時間を `millis()` に足す、の 3 つを raw の層に入れる。
- **領域の大きさ。** ほかのコアに、EEPROM の大きさをメニューで選ばせる例は無い(調査)。ライブラリかスケッチが大きさを宣言し、リンカーが末尾に置く形(EXP-04、使わなければ 0 B)が素直。

## 5. 進め方

1. 他の環境の調査を受け取り、1 の用途の表を埋め直す。
2. M1・M3 の未測定の系列を測る(V006、V203、V205、X315。OEP の口から M030、V407)。
3. M6 を実機で測る(ch32rv の各経路で、末尾に印を書いてから書き込み直す)。
4. M2 の周辺の振る舞い(UART の取りこぼし、PWM、DMA。USB は PC につながった X035 が無いので、V307 や L103 の USB で)。
5. M4 / M5 を、まず生の消去・書き込みで未測定の系列に広げ、候補の形式の試作ができたら commit の途中で行う。
6. M7、M8、M10、M11。M9 は、ベンチに入れない専用のチップを用意できたときだけ。
7. 候補を物差しで並べた表を作り、全体の形・面の大きさの決め方・書き込み直しで残す手段を、選択肢と推奨にして相談する。→ [decisions.ja.md](decisions.ja.md)
